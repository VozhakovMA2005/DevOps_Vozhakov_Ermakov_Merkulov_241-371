# Непрерывная интеграция AudFond

Программный документ к этапу 5 (ЛР №5). Основание: ТЗ **А.В.00001-01 33 01-1**,
подразделы 7.1 и 7.2.

CI — независимый обязательный барьер перед созданием и публикацией артефакта.
Барьер строится из тех же команд, что разработчик запускает у себя: сервер CI
не знает ни одной проверки, которой нет в `Makefile`.

```bash
make ci        # весь конвейер локально, в том же порядке, что на сервере
```

---

## 1. Почему локальные и серверные проверки совпадают

Если на сервере свой набор проверок, а у разработчика свой, возможны два
исхода, и оба плохие:

- **сервер строже** — разработчик узнаёт об ошибке только после отправки,
  через несколько минут ожидания, и правит «вслепую», коммит за коммитом;
- **сервер мягче** — то, что поймала бы локальная проверка, уходит в `main`.

Поэтому каждая стадия конвейера — это одна или несколько целей `make`.
Сервер CI вызывает их так же, как `make ci` вызывает их локально, и правило
одно: **новая проверка добавляется в `Makefile`, а не в настройки CI**. Тогда
«у меня проходит, а на сервере нет» означает разницу окружения (версия
Docker, сеть), а не разницу проверок, и воспроизводится одной командой.

Проверяется текущий код, а не прежняя копия: в контейнерном режиме образ
проверок пересобирается перед каждой проверкой (`docker compose run --build`,
неизменённые слои — из кэша), а поиск секретов, защита файлов приёмки и
проверка коммитов ветки идут на машине по рабочей копии git.

Версии инструментов тоже одни: ruff, mypy, bandit, pytest, pip-audit
закреплены в `requirements-dev.lock` с контрольными суммами, Trivy — точным
тегом образа.

## 2. Стадии

Названия и порядок первых девяти стадий — из ТЗ 7.1: lint → types → sast →
test → test-int → migrate-check → schema-check → secrets-scan → deps-check.
Следом — стадии, которых требует задание ЛР5: защита проверок, резервное
копирование, сборка, контейнерная проверка, анализ образа, публикация.

| № | Стадия | Цели make | Отчёт в `reports/` | Чем останавливает |
|---|---|---|---|---|
| 1 | lint | `quality` | `ruff.xml` | замечание линтера, неотформатированный файл |
| 2 | types | `types` | `mypy.xml` | ошибка типов |
| 3 | sast | `sast` | `bandit.json` | небезопасная конструкция в коде |
| 4 | test | `test-unit` | `junit-unit.xml` | упавший модульный тест |
| 5 | test-int | `test-int` | `junit-int.xml`, `coverage.xml`, `htmlcov/`, `coverage-services.json` | упавший интеграционный тест на PostgreSQL 17, покрытие ниже 70% общее или 80% по сервисному слою |
| 6 | migrate-check | `migrate-check` | — | миграция не откатывается или не накатывается повторно |
| 7 | schema-check | `schema-check` | — | схема после наката расходится с моделями (`alembic check`) |
| 8 | secrets-scan | `secrets`, `secrets-branch` | `secrets.json`, `secrets-branch.json` | секрет или запрещённый файл в дереве или в любом коммите ветки |
| 9 | deps-check | `deps-check` | `pip-audit.json` | известная уязвимость в закреплённой версии пакета |
| 10 | guard | `waivers`, `guard`, `ci-sync`, `codeowners-check` | `guard.md` | подавление без причины, удалённый тест, ослабленная проверка, расхождение CI и `make ci`, незакреплённый критический файл |
| 11 | backup | `restore-drill` | — | копия не восстанавливается или данные после восстановления не совпадают |
| 12 | build | `build-app` | — | многостадийный образ не собирается |
| 13 | container-check | `container-check` | `container-check.txt` | `latest`, root, секрет в образе, нет healthcheck, лишний порт, нет лимитов |
| 14 | image-scan | `image-scan` | `trivy.json` | уязвимость HIGH или CRITICAL с выпущенным исправлением |
| 15 | publish | `push` | — | выполняется, только если стадии 1–14 пройдены для этого же коммита |

Локально `make ci` проходит стадии 1–14 подряд; первая упавшая останавливает
конвейер. Сводка прохода — `reports/ci-summary.md`: стадии, время, итог.
После успешного прохода в `reports/ci-passed` записывается SHA коммита; в
начале каждого прохода отметка удаляется.

Порядок первых девяти стадий задан ТЗ. Все проверки, включая поиск
секретов и зависимости, стоят до сборки: образ из коммита, не прошедшего
любую из них, не собирается и не публикуется. Обратная сторона цепочки:
если упал тест, поиск секретов в этом прогоне не выполняется — его
результат будет в следующем прогоне, а локально — `make secrets-branch`.

## 3. Отдельная тестовая база

Тесты и учения не трогают рабочую базу:

- набор тестов на каждый прогон создаёт свою базу `audfond_test_<случайный
  суффикс>`, накатывает на неё миграции и удаляет её после прогона
  (`tests/conftest.py`);
- если базы нет, интеграционные тесты **падают, а не пропускаются**: сотня
  пропущенных тестов выглядит как зелёный прогон, и конвейер принял бы
  изменение, не проверив его на базе;
- `migrate-check` и `restore-drill` поднимают одноразовые базы и тоже их
  удаляют;
- роль, которой это разрешено, задаётся отдельно (`TEST_ADMIN_DSN`,
  `ADMIN_DATABASE_URL`) — роль приложения создавать базы не может (ТЗ 4.4).

На сервере CI база — отдельный контейнер PostgreSQL 17 на время прогона:
даже одноразовых баз рабочего сервера конвейер не видит.

## 4. Публикация образа

```bash
make registry-up                         # локальный реестр на 127.0.0.1:5000
make publish REGISTRY=localhost:5000     # make ci, и только при успехе — make push
make registry-ls                         # что опубликовано
```

`make push` (`scripts/push_image.sh`) не верит порядку стадий и проверяет сам:

1. **рабочее дерево чистое** — иначе образ не соответствовал бы коммиту;
2. **отметка `reports/ci-passed` записана для этого коммита** — `make ci`
   удаляет её в начале прохода и пишет только после того, как пройдены все
   стадии. Упала любая стадия — отметки нет — публикации нет;
3. **образ собран из этого коммита** — метка
   `org.opencontainers.image.revision` совпадает с SHA.

**Теги.** Образ всегда получает тег `sha-<полный SHA коммита>`: по тегу
однозначно находится коммит, а по коммиту — задача и запрос на слияние. Если
на коммите стоит аннотированный тег выпуска `vX.Y.Z`, образ получает и тег
версии `X.Y.Z`. Тег `latest` не ставится никогда (ТЗ 7.2): он означает «что
угодно, опубликованное последним», и развёртывание по нему невоспроизводимо.

**Реестры.**

| Реестр | Адрес | Вход |
|---|---|---|
| локальный («локальный docker hub») | `localhost:5000`, `make registry-up` | не нужен: слушает только 127.0.0.1 |
| реестр GitHub | `ghcr.io/<владелец>` | `docker login ghcr.io`; на сервере CI — токен из защищённых переменных |

Локальный реестр — `registry:3.0.0`: работает не от root, без возможностей
ядра, с файловой системой только для чтения; образы хранятся в
`~/.local/share/audfond-registry` и переживают перезапуск.

Учётные данные реестра в сценарий не передаются и в репозитории не хранятся:
вход выполняется заранее командой `docker login`.

**Из CI в локальный реестр.** Задача `publish-local` конвейера выполняется на
собственном исполнителе GitHub Actions (self-hosted runner) на машине
`audfond-app` и публикует тот же образ в `localhost:5000` стенда. Включается
переменной репозитория `LOCAL_REGISTRY=true`; без неё задача не создаётся и
не держит конвейер в ожидании выключенного стенда. Подробно — раздел 6.9.

## 5. Что защищает сами проверки

Барьер бесполезен, если его можно незаметно опустить. Поэтому:

- `make waivers` — подавление анализатора без причины, пропуск теста без
  причины, порог покрытия ниже ТЗ;
- `make guard` — удалённый тест, тест без проверок, шаг, убранный из
  `make verify`, убранная часть команды проверки или переменной, через
  которую она запускается, подавленная ошибка, новый файл настроек
  инструмента, правка сценария запуска проверок, ослабленные настройки
  анализаторов, новые исключения в сценариях (`docs/testing.md`, раздел 12);
- **guard-main** — те же сценарии guard и `ci-sync`, но в workflow
  `.github/workflows/guard-main.yml`, который GitHub берёт из `main`
  (событие `pull_request_target`). Ветка не может подменить ни сценарий,
  ни Makefile, ни `ci.yml` так, чтобы проверка этого не увидела: файлы
  запроса там только читаются как данные и не выполняются;
- критические файлы перечислены в `CONTRIBUTING.md` (раздел 5) и закреплены
  в `.github/CODEOWNERS`: их изменение одобряет ответственный участник.

Локальный `make guard` берёт сценарий из `main`, но Makefile — из ветки,
поэтому сам по себе он помощник автора, а не барьер. Барьер — guard-main и
обязательное одобрение ответственного.

## 6. GitHub Actions

CI-система — **GitHub Actions**: репозиторий на GitHub, и в нём же
встроенные правила защиты ветки, CODEOWNERS и реестр образов `ghcr.io`.
Конвейер — `.github/workflows/ci.yml`.

### 6.1. Когда запускается

| Событие | Что происходит |
|---|---|
| `push` в любую ветку | все стадии; публикации нет |
| создание и обновление запроса на слияние в `main` | все стадии; итог `ci-gate` — обязательная проверка: красный — слияние заблокировано |
| `push` в `main` (слияние запроса) | все стадии и публикация образа `sha-<SHA>` в `ghcr.io` |
| `push` тега `vX.Y.Z` | все стадии и публикация с тегами `sha-<SHA>` и `X.Y.Z` |
| `push` в `main` или тега при `LOCAL_REGISTRY=true` | дополнительно — публикация в локальный реестр стенда (`publish-local`) |
| вручную (Actions → CI → Run workflow) | все стадии |

Новый прогон той же ветки отменяет устаревший (`concurrency`); прогоны
`main` не отменяются.

### 6.2. Задачи

Каждая задача CI — одна стадия раздела 2 и вызывает те же цели `make`.
Девять проверок ТЗ идут **цепочкой в порядке ТЗ 7.1** (`needs`): упала одна —
следующие не запускаются, ошибка видна сразу, минуты не тратятся впустую.

```
config → lint → types → sast → test → test-int → migrate-check → schema-check
       → secrets-scan → deps-check → guard ─┐
                                   → backup ─┴→ build → container-check ─┐
                                                      → image-scan ──────┴→ ci-gate → publish
```

- **config** — проверяет, что защищённые переменные заданы, и падает с
  понятным сообщением, если нет.
- **test-int, migrate-check, schema-check, backup** — каждая со своим
  контейнером PostgreSQL 17 (`postgres:17.2-alpine`, тот же образ, что в
  `docker-compose.yml`). База живёт, пока идёт задача: даже одноразовых баз
  рабочего сервера конвейер не видит.
- **build** собирает образ один раз и передаёт его следующим задачам файлом:
  проверяется, анализируется и публикуется ровно тот образ, что собран.
- **ci-gate** ждёт все стадии и падает, если хоть одна не прошла, отменена
  или пропущена. Это единственная обязательная проверка в правиле защиты
  `main`: список стадий меняется в одном месте.
- **publish** ждёт `ci-gate` и запускается только для `main` и тегов выпуска.
- **guard-main** — отдельный workflow (`guard-main.yml`) на каждый запрос на
  слияние: защита проверок из `main`, вторая обязательная проверка правила.
- **publish-local** — то же, в локальный реестр стенда, на исполнителе
  `audfond-app` (раздел 6.9).

На сервере проверки идут в окружении `.venv` (`LOCAL=1`), а сборка и
анализ образа — в Docker. Цели те же, что в контейнерном режиме у
разработчика; `make LOCAL=1 ci` повторяет те же стадии и цели. Отличия
окружения: на сервере база — свой контейнер на задачу, BASE для guard
вычисляет `scripts/ci_base.sh`, а контейнерная проверка смотрит файлы и
образ без запущенных контейнеров.

### 6.3. Совпадение с make ci проверяется

`make ci-sync` (`scripts/ci_sync_check.py`, входит в стадию guard) сверяет
`ci.yml` со стадиями `scripts/ci_local.sh`:

- проверки ТЗ 7.1 есть и идут цепочкой в порядке ТЗ;
- у каждой стадии `make ci` есть задача CI с тем же именем и теми же целями
  `make`, и наоборот;
- `ci-gate` ждёт все стадии, публикация ждёт `ci-gate`;
- нет `continue-on-error` и подавленных ошибок `make`;
- действия — только `actions/*@vN` от GitHub и действия репозитория.

Добавить проверку в CI, забыв про `Makefile`, или ослабить задачу CI
незаметно не получится: `ci.yml` — критический файл, а расхождение роняет
стадию guard.

### 6.4. Защищённые переменные

| Переменная | Где | Зачем |
|---|---|---|
| `TEST_DB_PASSWORD` | Settings → Secrets and variables → Actions → Secrets | пароль тестовых баз PostgreSQL 17 в задачах CI |
| `GITHUB_TOKEN` | выдаётся GitHub на каждый прогон | вход в `ghcr.io` в задаче publish (право `packages: write` только у неё) |

Значения в журнале задач GitHub заменяет на `***`. В репозитории их нет;
`TEST_DB_PASSWORD` задаётся один раз:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(32))"
```

Остальные задачи получают только право чтения репозитория
(`permissions: contents: read`), `actions/checkout` не оставляет токен в
настройках git (`persist-credentials: false`).

### 6.5. Кэширование

| Что | Чем | Ключ |
|---|---|---|
| пакеты Python | `actions/setup-python`, `cache: pip` | содержимое `requirements.lock` и `requirements-dev.lock` |
| база уязвимостей Trivy | `actions/cache`, `~/.cache/audfond-trivy` | дата: база обновляется ежедневно |

Кэш ускоряет, но не подменяет проверку: пакеты из кэша ставятся с
`--require-hashes`, контрольные суммы сверяются.

### 6.6. Отчёты

Каждая задача выкладывает `reports/` как артефакт прогона
(`reports-<задача>`, хранится 14 дней), даже при сбое — тогда он нужнее
всего. Отчёт защиты проверок (`guard.md`) и покрытие сервисного слоя
выводятся в сводку прогона на странице Actions.

### 6.7. Сторонние действия не используются

Только `actions/checkout`, `setup-python`, `cache`, `upload-artifact`,
`download-artifact` от GitHub и действие репозитория
`.github/actions/checks-env`. В марте 2026 года теги `trivy-action` были
подменены вредоносным кодом, крадущим токены CI: поэтому сканер образа
запускается сценарием проекта из закреплённого образа Trivy, а вход в реестр
— командой `docker login`, без сторонних действий.

### 6.8. Защита main: CODEOWNERS и правило ветки

ТЗ 7.1: критические файлы приёмки защищаются правилами CODEOWNERS, их
изменение требует отдельного одобрения ответственного участника; при
падении хотя бы одной проверки запрос на слияние технически блокируется.

**`.github/CODEOWNERS`** закрепляет за ответственными конвейер CI, `Makefile`,
настройки анализаторов, тесты, Dockerfile и compose, lock-файлы, файлы
развёртывания и сценарии проверок. У каждого пути два-три ответственных:
автор запроса сам себя одобрить не может — одобряет второй.

`make codeowners-check` (стадия guard) следит, чтобы файл не отставал от
жизни: каждый критический файл репозитория (список `CRITICAL` в
`acceptance_guard.py` — один на обе проверки) закреплён, у каждого правила не
меньше двух ответственных, вместо логинов не остались заглушки.

**`.github/rulesets/main.json`** — правило защиты `main`, хранится в
репозитории и импортируется в настройки:

| Правило | Что даёт |
|---|---|
| `pull_request`: 1 одобрение, `require_code_owner_review` | изменение критического файла не сливается без одобрения его ответственного |
| `dismiss_stale_reviews_on_push`, `require_last_push_approval` | одобрение снимается новым коммитом: нельзя получить одобрение и потом дописать |
| `required_review_thread_resolution` | незакрытое замечание ревьюера блокирует слияние |
| `allowed_merge_methods: squash` | только Squash and Merge (CONTRIBUTING 2.8) |
| `required_status_checks`: `ci-gate` и `guard-main` от GitHub Actions, ветка свежая | красный конвейер или ослабление проверок — кнопка слияния недоступна |
| `non_fast_forward`, `deletion`, `required_linear_history` | нет `push --force` в `main`, ветку нельзя удалить, история линейна |
| `bypass_actors: []` | исключений нет ни для кого, включая администраторов |

Прямой push в `main` запрещён правилом `pull_request`: изменение попадает в
`main` только через запрос на слияние.

Импорт (один раз, нужны права администратора репозитория):

```bash
gh api --method POST repos/<владелец>/<репозиторий>/rulesets \
  --input .github/rulesets/main.json
```

или Settings → Rules → Rulesets → New ruleset → Import a ruleset.

Для приватного репозитория правила веток на бесплатном тарифе не
применяются: нужен GitHub Pro (бесплатно по GitHub Student Developer Pack)
или публичный репозиторий.

### 6.9. Исполнитель на стенде и локальный реестр

Реестр стенда слушает только `127.0.0.1:5000`: серверам GitHub до него не
достать. Поэтому публикацию в него выполняет собственный исполнитель
(self-hosted runner), установленный на `audfond-app` с меткой `audfond`, от
пользователя `deployer` (он в группе `docker`).

| Мера | Зачем |
|---|---|
| задача только для `push` в `main` и тегов выпуска | код из запросов на слияние на машине стенда не выполняется никогда — только уже одобренный и прошедший `ci-gate` |
| Settings → Actions → «Require approval for all outside collaborators» | запрос на слияние из чужого форка не запустит свой вариант конвейера без одобрения |
| включение переменной `LOCAL_REGISTRY` | стенд выключен — задача не создаётся, конвейер не ждёт исполнителя |
| `make push` со всеми проверками | на исполнителе действует тот же барьер: SHA, чистое дерево, метка коммита |

Установка исполнителя — Settings → Actions → Runners → New self-hosted
runner (Linux x64): страница показывает команды загрузки и
`./config.sh --url … --token …`; при настройке указать метку `audfond`, затем
`sudo ./svc.sh install deployer && sudo ./svc.sh start`. Пошагово — гайд
«Прогон и показ», шаг про исполнитель.

# ЛР6 — прогон и показ на защите

## До защиты

Разверните отдельную VM по гайду. Начните с выключенного CD_ENABLED и successful bootstrap SHA-образа 0.6.0. Не пытайтесь использовать прежний 0.5.0 как базу без проверки: у ЛР5 метка commit могла быть сокращенной, а ЛР6 требует полный SHA и строгую приемку. Для демонстрации двух версий используйте два образа, собранных уже после исправления полного SHA.

Сохраните ссылки на Issue, PR, CI, publish и release-history. На экране покажите Docker compose ps, /version, JSON состояния и само приложение. Шаблон evidence-template.md заполняется только фактическими значениями.

## Сквозной выпуск контрольной функции

Контрольная функция — уточнение подписи каталога помещений. Это маленькая пользовательская функция, которую удобно проследить от Issue до целевого браузера. Она не меняет схему БД.

```bash
git switch main
git pull --ff-only
# Создайте Issue «Уточнить заголовок каталога помещений», запишите реальный номер.
ISSUE=ACTUAL_ISSUE_NUMBER
git switch -c "feat/$ISSUE-catalog-title"
rg -n 'Каталог|Помещения' project/app/web/templates
# Измените заголовок каталога на «Каталог аудиторного фонда» в найденном шаблоне.
cd project
make verify
make guard
make ci
cd ..
git add project/app/web/templates
git commit -m "feat(web): уточнить заголовок каталога (#$ISSUE)" -m "Единое название каталога для пользователей. Refs #$ISSUE"
git fetch origin
git rebase origin/main
git push -u origin HEAD
```

Откройте PR с тем же заголовком, что у Issue, и Closes #<реальный номер> в первой строке. После содержательного ревью, Approve и зеленого CI выполните Squash and Merge. CI для main публикует sha-<merge SHA>; deploy-staging получает именно его. Убедитесь, что CD зеленый, /version.commit равен merge SHA, вход и каталог работают, новый заголовок виден в браузере. Сохраните SHA/digest A принятого выпуска.

## Неверный тег

```bash
sudo -iu audfond-cd
python3 /opt/audfond-cd/cd.py deploy --tag latest
echo $?
python3 /opt/audfond-cd/cd.py deploy --tag 99.99.99
echo $?
python3 /opt/audfond-cd/cd.py check
```

latest отбрасывается локально до обращения в registry; отсутствующий 99.99.99 отвергается docker pull. Оба возвращают ненулевой код, текущий релиз и previous не изменяются. Верните действия на стенде в обычное состояние перед следующим опытом.

## Отсутствующая переменная

Сделайте защищенную копию app.env вне Git. В тестовом app.env временно очистите JWT_SECRET. Повторный deploy должен отказать на preflight, еще до замены контейнеров. Убедитесь, что старый URL продолжает работать. Восстановите файл из защищенной копии и права 600. Не печатайте env целиком на демонстрации.

## Недоступный registry

Скопируйте deploy.env в защищенный backup, временно поставьте IMAGE_REPOSITORY=127.0.0.1:59999/audfond. Запустите deploy существующего по формату тега. Pull должен отказать до изменения стека и до записи pending. Сравните /version с исходным SHA, затем восстановите deploy.env. Этот способ не отключает сеть работающей базы или приложения.

## Неуспешный healthcheck

Не создавайте бессмысленный PR с отключением проверок. На НОВОМ тестовом кандидате, уже опубликованном успешным CI, временно задайте в app.env APP_PORT=8001 (proxy и healthcheck ожидают 8000), предварительно сохранив app.env с правами 600. Потребуется второй принятый образ с другим digest, иначе повтор того же образа выполнит только check.

Выполните deploy второго образа. Ожидается отказ --wait. Поскольку конфигурация общая для релизов, она испортит и попытку автоматического возврата: состояние честно останется pending с recovery-failed. Сразу восстановите app.env из backup, выполните recover и check. /version обязан вернуть последний принятый образ. Это дополнительно показывает восстановление после неисправной конфигурации.

Отдельный простой тест здоровья: остановите app и выполните check; команда должна отказать, current не меняется. Затем выполните recover только при наличии pending либо перезапустите контейнер обычным compose up и снова check.

## Приложение запустилось, но каталог не работает

Эта проверка должна идти на опубликованном дефектном образе и показать автоматический возврат без смены env. Создайте отдельный временный демонстрационный fork репозитория со своим GHCR-пакетом и копией защищенной тестовой VM. Не сливайте намеренную поломку в учебный main и не ослабляйте его CI.

В fork создайте задачу и ветку для эксперимента. Добавьте в app/api/rooms.py только в обработчик list_rooms условие по новой переменной окружения DEMO_BREAK_CATALOG: если true, вернуть существующий стандартный error_response(503, "DEMO_CATALOG_FAILURE", "Учебный отказ каталога"). В обычных тестах переменная отсутствует — это намеренно моделирует ошибку, проявляющуюся лишь в целевой среде. CI не отключать. Рецензент согласует эксперимент, feature PR проходит CI, публикуется в fork main с отдельным SHA. На копии стенда IMAGE_REPOSITORY должен указывать на пакет fork и иметь два образа с теми же правилами version/revision/schema.

На КОПИИ стенда сначала примите исправный образ A, затем в app.env добавьте DEMO_BREAK_CATALOG=true и выпустите дефектный образ B. У A этой экспериментальной ветки кода нет, поэтому он игнорирует новую переменную. B запускается healthy, /healthz и /readyz отвечают 200, /version правильный, но запрос каталога дает 503. Автоматический возврат A обязан пройти, деплой B обязан завершиться ненулевым кодом; история — started → failed → restored, current остается A, previous не указывает на B. Удалите экспериментальную переменную после опыта. Сохраните реальные доказательства, затем удалите экспериментальную среду по правилам команды.

Быстрый вариант без отдельного образа — временно неверный SMOKE_PASSWORD: приложение healthy, приемка входа падает; однако тот же неверный пароль испортит проверку A, поэтому это тест recovery-failed, а не доказательство успешного автоматического возврата. Не выдавайте его за предыдущий сценарий.

## Ручной rollback

На основном отдельном стенде примите два ИСПРАВНЫХ SHA-образа A и C через разные коммиты main. Сохраните current/previous. Actions → CD manual → main → rollback. Дождитесь результата. /version.commit обязан совпасть с A, current.image — с ранее сохраненным digest A; check повторно проходит. История — accepted с operation=rollback. Для возврата C можно повторить rollback или deploy его SHA-тега.

## Готовые помощники для опытов

Для первых четырех отрицательных проверок есть project/deploy/cd/drills.sh. Скопируйте его на staging, просмотрите и запустите от audfond-cd с SHA-тегом ДРУГОГО опубликованного исправного образа. Скрипт временно меняет только staging env, восстанавливает их через trap и выполняет recover после теста APP_PORT. Два запуска одновременно недопустимы.

```bash
bash drills.sh sha-FULL_40_HEX_SHA_OF_ANOTHER_IMAGE
```

Условный дефект каталога можно внести готовым помощником только в новый checkout демонстрационного fork:

```bash
python3 project/deploy/cd/make_demo_patch.py --fork-checkout /path/to/disposable-fork --confirm-disposable-fork
# В fork: просмотреть diff, make verify, make guard, make ci, ревью и публикация.
```

## Два одновременных запуска и прерывание

Покажите, что две Actions-задачи используют группу audfond-staging-delivery, cancel-in-progress=false. Для явного теста серверной блокировки удерживайте flock в отдельном терминале и вызовите check из другого:

```bash
flock /srv/audfond-staging/deploy.lock -c 'read -r -p "Блокировка удерживается; Enter для освобождения"'
# Во втором терминале: cd.py check → «Другое развертывание уже выполняется», exit 1.
```

При имитации прерывания используйте только тестовую VM и завершайте контроллер после появления pending. Следующая доставка отклоняется, recover возвращает current и повторяет приемку. Если это самый первый bootstrap без current, используйте процедуру разбора первого запуска из гайда.

## Что собрать в доказательства

Для каждого опыта: время UTC, действие, ожидаемый результат, фактический exit code, current/previous до и после, /version без секретов, ссылка на job, строки release-history. Не подставляйте выводы из unit-тестов вместо результата живого деплоя. На защите явно разделяйте ошибку публикации CI и ошибку проверки работающего релиза CD.

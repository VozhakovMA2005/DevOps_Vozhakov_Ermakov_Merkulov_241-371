# Развёртывание, диагностика, восстановление

Два способа, оба обязательны по ТЗ 4.5: **в контейнерах** (этап 1) и
**на Linux-сервере без контейнеров** (этап 2, лабораторная работа №2).

---

## 1. Стенд этапа 2

Две машины Debian 12 или 13 **без графического интерфейса**, VirtualBox.

| Узел | Имя | Адрес | Что на нём |
|---|---|---|---|
| Сервер приложения | `audfond-app` | 192.168.56.10 | Python, виртуальное окружение, служба systemd |
| Сервер базы | `audfond-db` | 192.168.56.11 | PostgreSQL 17 |
| Хост-машина | — | 192.168.56.1 | клиент браузера и «посторонний узел» для проверки |

Сетевых интерфейсов у каждой машины два: первый NAT — для установки пакетов,
второй Host-only — внутренняя сеть стенда с постоянными адресами.

### Учётные записи

| Пользователь | Для чего | Вход |
|---|---|---|
| `deployer` | администрирование, развёртывание | по ключу SSH, есть `sudo` |
| `audfond` | запуск приложения | **нет**: системная запись без оболочки и пароля |
| `root` | — | удалённый вход **запрещён** |

### Роли базы данных

| Роль | Права | Кто использует |
|---|---|---|
| `af_owner` | владеет схемой, выполняет миграции | скрипт развёртывания |
| `af_app` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` на данные | приложение |

Разделение осознанное: у приложения нет прав менять схему. Даже если его
захватят, уронить таблицу через него нельзя — прав нет на уровне СУБД, а не на
уровне кода. Проверяется одной командой:

```bash
psql "postgresql://af_app@192.168.56.11/audfond" -c "DROP TABLE room;"
# ERROR: must be owner of table room
```

## 2. Порядок развёртывания

Скрипты лежат в `deploy/`. Каждый можно запускать повторно: они не плодят
дубликаты и не ломают уже настроенное.

### Шаг 1. Базовая подготовка — на обеих машинах

```bash
# на audfond-db, от root
ROLE=db PUBKEY="$(cat ваш_ключ.pub)" ADMIN_PASSWORD='…' bash deploy/01-base.sh

# на audfond-app
ROLE=app PUBKEY="$(cat ваш_ключ.pub)" ADMIN_PASSWORD='…' bash deploy/01-base.sh
```

Делает: имя узла, записи в `/etc/hosts`, постоянный адрес, пользователя
`deployer` с входом по ключу, запрет входа под root и по паролю, межсетевой
экран с закрытым входящим трафиком.

`ADMIN_PASSWORD` — пароль **не для входа**, по SSH пароли запрещены вовсе.
Он нужен для `sudo`: тот спрашивает пароль самого пользователя, и без него
`deployer` не смог бы выполнить ни одной команды с правами root.

После этого с хост-машины работает вход по ключу, а файлы переносятся тем же
ключом, без паролей:

```bash
ssh deployer@192.168.56.11
scp -r deploy deployer@192.168.56.11:~/
```

### Шаг 2. Сервер базы данных

```bash
# на audfond-db, от root
OWNER_PASSWORD='…' APP_PASSWORD='…' bash deploy/02-db-server.sh
```

Делает: ставит PostgreSQL 17 из официального репозитория, заставляет его
слушать только внутренний адрес, разрешает подключения **только** с
192.168.56.10 и только ролям `af_owner` и `af_app`, создаёт базу и роли,
открывает порт 5432 только серверу приложения.

Пароли сохраняются в `/etc/audfond/db-passwords` с правами 600 и владельцем
root. В репозитории их нет.

### Шаг 3. Сервер приложения

```bash
# на audfond-app, от root
bash deploy/03-app-server.sh
```

Делает: ставит Python и сборочные пакеты, создаёт системного пользователя
`audfond` без оболочки, готовит каталоги с правами, ставит службу systemd и
включает её в автозапуск, открывает порт 8000.

Затем впишите настройки:

```bash
sudo nano /etc/audfond/audfond.env
```

Нужны адрес базы с паролем роли `af_app` и ключ подписи токенов:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

### Шаг 4. Выкладка

Скопируйте пароль роли-владельца с сервера базы и запустите:

```bash
# на audfond-app, от deployer
sudo OWNER_PASSWORD='…' bash deploy/deploy.sh
```

Делает: переносит код, собирает виртуальное окружение по закреплённым версиям,
накатывает миграции под ролью владельца, раздаёт права роли приложения,
перезапускает службу и ждёт ответа `/readyz`.

### Шаг 5. Первый администратор

```bash
# на audfond-app, от deployer
sudo bash deploy/manage.sh create-admin
```

Скрипт спросит логин, ФИО и пароль с клавиатуры — пароль не попадёт ни в
историю оболочки, ни в список процессов. Создаётся пользователь с ролью
`SYS_ADMIN` (ТЗ 4.1.1). Команда идемпотентна: если такой логин уже есть,
ничего не меняется.

Запускать `scripts/create_admin.py` напрямую не нужно и не получится:
настройки лежат в `/etc/audfond/audfond.env`, и подставляет их systemd
(`EnvironmentFile`). При запуске руками этого никто не делает, поэтому
python не увидит `DATABASE_URL` и откажется работать. `manage.sh` читает
тот же файл сам и запускает команду от имени служебного пользователя.

Проверить, что приложение вообще принимает настройки:

```bash
sudo bash deploy/manage.sh check-config
```

Приложение доступно с хост-машины: **http://192.168.56.10:8000/**

## 3. Управление службой

```bash
sudo systemctl start audfond        # запустить
sudo systemctl stop audfond         # остановить
sudo systemctl restart audfond      # перезапустить
sudo systemctl status audfond       # состояние
sudo systemctl enable audfond       # автозапуск при загрузке
journalctl -u audfond -f            # журнал, непрерывно
journalctl -u audfond -n 50         # последние 50 строк
```

Миграции службой **не выполняются**: накат схемы — шаг развёртывания, а не шаг
запуска. У пользователя, от которого работает служба, прав менять схему нет.

## 4. Проверка стенда

```bash
sudo bash deploy/check.sh
```

Проверяет по пунктам защиты: служба включена и работает, работает не от root,
настроен перезапуск после сбоя, служебные адреса отвечают, порт слушается,
база доступна с сервера приложения, лишних портов нет, вход под root и по
паролю запрещён, межсетевой экран включён, настройки лежат вне кода и закрыты
от посторонних.

### Что показывают на защите

**Перезагрузка обеих машин и автозапуск.** Перезагрузите сначала базу, потом
приложение; после загрузки `systemctl is-enabled audfond` отвечает `enabled`,
а `/readyz` — 200.

**Остановка базы и диагностика.**

```bash
# на audfond-db
sudo systemctl stop postgresql

# на audfond-app
curl -s http://127.0.0.1:8000/healthz   # 200: процесс жив
curl -s http://127.0.0.1:8000/readyz    # 503 DB_UNAVAILABLE
journalctl -u audfond -n 20
```

Служба при этом **не падает** — в этом и смысл двух разных адресов.

**Поиск процесса, порта и журналов.**

```bash
systemctl status audfond            # состояние и главный процесс
ps -ef | grep uvicorn               # процессы
ss -ltnp | grep 8000                # кто слушает порт
journalctl -u audfond --since "10 min ago"
```

**Изменение параметра службы и возврат.**

```bash
sudo systemctl edit audfond         # например, RestartSec=15s
sudo systemctl daemon-reload && sudo systemctl restart audfond
systemctl show -p RestartSec audfond
sudo systemctl revert audfond       # вернуть как было
```

**Недоступность базы с постороннего узла.** С хост-машины (192.168.56.1):

```bash
# PowerShell
Test-NetConnection 192.168.56.11 -Port 5432    # TcpTestSucceeded : False
```

Порт закрыт межсетевым экраном для всех, кроме 192.168.56.10. При этом с
сервера приложения он доступен:

```bash
# на audfond-app
timeout 3 bash -c '</dev/tcp/192.168.56.11/5432' && echo "база доступна"
```

## 5. Диагностика

| Симптом | Где смотреть |
|---|---|
| служба не запускается | `journalctl -u audfond -n 50` — причина в последних строках |
| `/readyz` отдаёт `DB_UNAVAILABLE` | база не запущена, неверный адрес или пароль, закрыт порт |
| `/readyz` отдаёт `MIGRATIONS_NOT_APPLIED` | выполните `deploy.sh` |
| приложение не стартует, пишет про `JWT_SECRET` | ключ не задан в `/etc/audfond/audfond.env` |
| страница не открывается с хост-машины | `sudo ufw status` на сервере приложения, порт 8000 |
| не пускает по SSH | вход по паролю запрещён — нужен ключ; проверьте `AllowUsers` |
| ответ 500 | найдите `request_id` из ответа: `journalctl -u audfond \| grep <id>` |

Журнал структурированный, в формате JSON: время, уровень, тип события, адрес,
результат, идентификатор запроса. Пароли и токены в журнал не пишутся.

## 6. Резервное копирование и восстановление

```bash
# на audfond-db
sudo -u postgres pg_dump -Fc audfond > /var/backups/audfond-$(date +%F-%H%M).dump
sudo -u postgres pg_restore -d audfond --clean --if-exists /var/backups/audfond-….dump
```

В контейнерном варианте то же самое делают `make backup` и
`make restore FILE=…`.

Проверять восстановление надо сразу: удалите тестовую запись, восстановитесь
из копии и убедитесь, что запись вернулась. Копия, которую ни разу не
разворачивали, — это не копия.

## 7. Развёртывание в контейнерах

```bash
cp .env.example .env
python3 -c "import secrets; print(secrets.token_urlsafe(48))"   # в JWT_SECRET
make up
make create-admin
```

Устройство образа: многостадийная сборка, процесс от пользователя с uid 10001,
теги базовых образов закреплены, объявлен `healthcheck`, заданы ограничения
ресурсов, порт базы наружу не публикуется, `exec uvicorn` в точке входа —
процесс сам получает `SIGTERM`.

Проверить перечисленное: `make container-check`.

# ЛР7. Управление конфигурацией стенда AudFond

Ansible приводит выделенный стенд к состоянию из репозитория. На стенде используется проверенный опубликованный образ AudFond из GHCR. Контроллер доставки из ЛР6 запускает PostgreSQL, приложение и nginx. Та же проверка контроллера подтверждает готовность контейнеров, версию, вход и каталог.

## Инвентарь и зоны ответственности

Применение рассчитано на отдельную Ubuntu Server 24.04 или 26.04 x86-64. До прогона подготовьте доступ пользователя `labadmin` по SSH-ключу, sudo и подтверждённый ключ сервера. Для первого применения нужен чистый узел с именем из inventory. Повторное применение идёт на уже управляемом узле того же окружения.

| Уровень | Где задаётся | Что задаётся |
| --- | --- | --- |
| Общий | `infra/inventory/group_vars/all.yml` | пользователь подключения, параметры Docker и AudFond, образ по полному SHA |
| Окружение | `infra/inventory/group_vars/{lab,staging}.yml` | имя базы и локальный HTTP-порт |
| Узел | `infra/inventory/host_vars/` | адрес подключения и проверяемое имя машины |
| Секретный | личный файл Ansible Vault вне рабочего дерева | `vault_db_password`, `vault_jwt_secret`, `vault_smoke_password` |

`lr7-lab` использует `audfond_lab` и `127.0.0.1:18081`. `lr7-staging` использует `audfond_staging` и `127.0.0.1:18080`. Каждый запуск ограничивается выбранным узлом. Привязки к именам защищают уже работающие стенды команды от случайного применения.

Храните пароль Vault и закрытый SSH-ключ у оператора. В шаблонах остаются ссылки на переменные. На узле каталоги с настройками доступны служебной учётке `audfond-cd`, файлы с параметрами записываются с режимом `0600`. Шаги обработки секретов подавляют журналы и diff. После повторного запуска используйте тот же Vault выбранного окружения.

## Требования к ревью

- **Сеть.** Входящий firewall закрыт по умолчанию. Разрешён TCP 22 для управления с указанного в inventory источника. HTTP слушает loopback, доступ для показа идёт через SSH-туннель. PostgreSQL остаётся во внутренней сети Docker.
- **Учётки.** Администрирование ОС выполняется пользователем `labadmin` через SSH-ключ и sudo. Учётка `audfond-cd` используется локально сервисом доставки, её пароль заблокирован и интерактивный вход выключен. Управление Docker даёт высокие полномочия на узле, поэтому стенд выделен под AudFond.
- **Команды.** Используйте Ansible-модули для состояния, которое они поддерживают. Для запуска штатной команды используйте `ansible.builtin.command` с `argv`. Диагностическая команда явно помечается `changed_when: false`. Объясняйте любое применение shell в описании PR.
- **Повторяемость.** Пакеты устанавливаются без принудительного обновления на каждый прогон. Шаблоны и контроллер пересоздают управляемое состояние только при изменении. Укажите конкретный опубликованный SHA и проверьте чистый запуск, повтор с `changed=0` и восстановление конфигурации.
- **Секреты.** В PR проверяйте шаблоны, файлы inventory и историю на открытые ключи, токены и пароли. Значения обнаруженных секретов не выводятся. Преднамеренную ошибку для отрицательной проверки держите в отдельной временной копии, не коммитьте её.

## Проверка в GitHub Actions

Отдельный workflow `infra` запускается на PR в `main`, при обновлении `main` и вручную. Задание `infra-check` с правом чтения устанавливает Ansible из `infra/requirements.txt` и коллекцию из `infra/requirements.yml`, затем проверяет inventory, синтаксис playbook и открытые секреты. Проверка не подключается к ВМ и не использует Vault. Работа приложения, повторный прогон и восстановление конфигурации подтверждаются на отдельной ВМ.

Локальная проверка после установки этих же зависимостей:

```bash
make -C infra check
```

## Обязательное согласование

`.github/CODEOWNERS` назначает ответственных за всё дерево `infra/`, включая роли, шаблоны, параметры и сценарии проверок. Правило `.github/rulesets/main.json` требует одобрения Code Owner и зелёных `ci-gate`, `guard-main` и `infra-check`. Оно также сохраняет прежние правила squash-merge, защиты от force push и повторного одобрения после новых коммитов.

1. Слейте проверенный PR, который впервые добавляет workflow `infra`. Дождитесь зелёного `infra-check` в GitHub Actions.
2. Владелец репозитория открывает **Settings → Rules → Rulesets**. Если правила ещё нет, импортирует `.github/rulesets/main.json` через **New ruleset → Import a ruleset**. Если правило уже действует, обновляет его и добавляет `infra-check` от GitHub Actions к имеющимся обязательным проверкам.
3. Сохраните правило активным для `main`. На PR с изменением под `infra/` проверьте, что GitHub запрашивает одобрение Code Owner и блокирует слияние без него. Участникам, указанным в CODEOWNERS, требуется доступ на запись.

Настройки GitHub начинают действовать после применения в интерфейсе репозитория. JSON и CODEOWNERS фиксируют требования к настройке и рецензированию. [Правила GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)

## Приёмка на стенде

1. В журнале первого запуска показать, что чистый Linux-узел подготовлен и доступность AudFond проверена.
2. На том же узле с теми же параметрами показать повторное применение с `changed=0`.
3. Изменить управляемый параметр на учебной ВМ, повторить применение и показать восстановленное состояние.
4. Показать HTTP 200 от `/version`, ожидаемый SHA и принятую контроллером проверку основного сценария.
5. Показать успешный `infra-check` без паролей в отчёте и отрицательную проверку на искусственном значении во временной копии.

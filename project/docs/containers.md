# Контейнерное окружение AudFond

Программный документ этапа 4 (ЛР №4): контейнеризация и автоматическая
проверка окружения. Основание — подраздел 4.5 и раздел 7 ТЗ.

Связанные файлы:

| Файл | Что в нём |
|---|---|
| `docker/Dockerfile` | образ приложения: стадии `builder`, `runtime`, `test` |
| `docker/entrypoint.sh` | точка входа: `serve`, `migrate`, `admin` |
| `docker/nginx/default.conf`, `proxy.inc` | Nginx перед двумя экземплярами |
| `.dockerignore` | что не попадает в контекст сборки |
| `docker-compose.yml` | службы, сети, том, healthcheck, порядок запуска, лимиты |
| `.env.docker.example` | образец настроек; рабочий `.env.docker` создаёт `make docker-env` |
| `requirements.lock`, `requirements-dev.lock` | все пакеты с версиями и контрольными суммами |
| `scripts/container_check.py` | `make container-check` |
| `scripts/preflight.sh` | `make preflight`: проверка машины до запуска |
| `scripts/container_backup.sh`, `container_restore.sh` | копия и восстановление в контейнерах |
| `scripts/container_drill.sh` | учения: сохранность, завершение, отказ узла, новый том |

## 1. Где работает Docker

На стенде — внутри виртуальной машины `audfond-app` (Debian). Контейнерам не
нужна аппаратная виртуализация хоста: это процессы ядра Linux той же
виртуальной машины, изолированные пространствами имён. Стенд ЛР2 на машине
остаётся как был и не мешает: служба `audfond` слушает порт 8000, контейнерное
окружение — 8080.

Рекомендуемые ресурсы виртуальной машины: 2 vCPU, 2 ГБ памяти, 10 ГБ диска.

Установка (от `deployer`, один раз):

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL --retry 5 --retry-delay 3 https://download.docker.com/linux/debian/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
ls -l /etc/apt/keyrings/docker.asc   # файл должен быть, иначе дальше не идти
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/debian $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker deployer      # затем выйти и зайти по ssh заново
docker compose version
```

Если репозиторий Docker недоступен, подойдут пакеты Debian: убрать
`/etc/apt/sources.list.d/docker.list`, затем
`sudo apt-get install -y docker.io docker-compose docker-buildx` и проверить,
что работает именно `docker compose version` (вторая версия, с пробелом).

Если образы не скачиваются с Docker Hub (ошибка `403` или таймаут), можно
указать зеркало в `/etc/docker/daemon.json` и перезапустить Docker:

```json
{ "registry-mirrors": ["https://mirror.gcr.io"] }
```

Членство в группе `docker` равносильно правам root на машине. Для учебного
стенда это допустимо; в эксплуатации доступ к Docker выдаётся отдельной ролью.

## 2. Запуск

```bash
cd ~/audfond
make docker-env     # .env.docker со случайными паролями, права 600 (один раз)
make preflight      # проверка машины: Docker, образы, права, порт, диск
make up             # preflight → сборка → make container-check → запуск, ждёт healthy
make ps             # состояние служб
make create-admin   # первый администратор: логин и пароль — в .env.docker
make seed           # демонстрационные данные (по желанию)
```

Сервис: `http://192.168.56.10:8080/`. Других опубликованных портов нет.

С момента, когда создан `.env.docker` и Docker запущен, команды `make`
выполняются в контейнерах: `make migrate`, `make backup`, `make verify` и
остальные. Текущий способ показывает `make mode`; принудительно —
`make LOCAL=1 …` (стенд ЛР2–3) и `make LOCAL=0 …` (контейнеры).

## 3. Схема окружения

```
клиент ──:8080──► nginx ──┬──► app1 ──┐
             (frontend)   └──► app2 ──┴──► db        backend: internal
                               migrate ──► db        одноразово, до app1 и app2
```

| Служба | Образ | Сети | Порт наружу | Назначение |
|---|---|---|---|---|
| `db` | `postgres:17.2-alpine` | backend | нет | PostgreSQL, данные на томе `audfond_db-data` |
| `migrate` | `audfond:0.5.0` | backend | нет | накатывает миграции и выходит |
| `app1`, `app2` | `audfond:0.5.0` | backend, frontend | нет | два экземпляра приложения |
| `nginx` | `nginxinc/nginx-unprivileged:1.27.3-alpine` | frontend | 8080 | единственная точка входа |
| `tests` | `audfond-tests:0.5.0` | backend | нет | `make verify` в контейнере, по требованию |

Сеть `backend` объявлена `internal`: у неё нет выхода наружу, а база в ней
недоступна ни с машины, ни из интернета. Nginx в эту сеть не входит и к базе
обратиться не может.

## 4. Как выполнены пункты задания

### 4.1. Dockerfile и .dockerignore (пункт 1)

Три стадии. `builder` ставит пакеты в виртуальное окружение `/opt/venv`;
`runtime` получает только это окружение и код — без кэша pip и без файлов
сборки; `test` добавляет инструменты проверок и в бой не идёт.

`.dockerignore` отсекает файлы окружения (`.env`, `.env.*`), ключи, `.git`,
виртуальные окружения, кэши, копии базы и отчёты. Это и защита секретов, и
скорость: контекст сборки — только то, что нужно образу.

### 4.2. Воспроизводимая сборка (пункт 2)

- Базовый образ закреплён точной версией `python:3.12.16-slim` (до ЛР5 —
  `3.12.8-slim`, обновлён по результатам анализа образа, раздел 8).
- `requirements.lock` закрепляет все 35 пакетов приложения, включая
  транзитивные, и для каждого — контрольные суммы файлов. Сборка идёт с
  `pip install --require-hashes --no-deps`: если на сервере подменён файл или
  пришла другая версия, сборка падает, а не тихо берёт новое.
- Слой зависимостей отделён от кода: пока lock-файл не менялся, он берётся из
  кэша, и две сборки одного коммита дают одинаковый набор пакетов.
- Скачанные пакеты складываются в кэш сборки на машине (`RUN --mount=type=cache`),
  а не в образ: если загрузка с PyPI оборвалась, повторный `make up` докачивает
  только недостающее. Таймаут pip — 120 секунд, до 10 повторов. Контрольные
  суммы проверяются и для пакетов из кэша.
- Сборка без служебных аттестаций (`BUILDX_NO_DEFAULT_ATTESTATIONS=1` в
  `Makefile`): с ними каждая сборка даёт новый идентификатор образа даже без
  изменений. Без них тот же вход даёт тот же образ, и повторный `make up` не
  пересоздаёт работающие контейнеры.
- `make container-check` сверяет `pip freeze` внутри образа с lock-файлом.

Lock-файл обновляется командой `make lock` (нужен `pip-tools`) — только
осознанно, в отдельной задаче.

### 4.3. Непривилегированный пользователь (пункт 3)

Приложение работает от пользователя `audfond` с uid 10001 (`USER 10001:10001`).
Код в образе принадлежит root и только читается: процесс не может изменить
сам себя. Права на код выставляются при сборке явно (`chmod -R u=rwX,go=rX`):
`COPY` переносит права из рабочего каталога как есть, и если там файлы
закрыты (600, каталоги 700), пользователь приложения не прочитает код —
Python увидит пакет без `__init__.py` и упадёт на импорте. `make container-check`
проверяет это отдельно: запускает импорт приложения от пользователя образа. Дополнительно у всех служб: `no-new-privileges`, `cap_drop: ALL`,
у приложения и Nginx — файловая система только для чтения (`read_only`), запись
лишь во временный каталог в памяти.

Nginx — вариант образа без root (uid 101, порт 8080). PostgreSQL при первом
запуске меняет владельца каталога данных и сразу переходит на пользователя
`postgres`; для этого ему возвращены пять возможностей ядра, сам сервер
работает не от root. Проверяется по фактическим процессам:
`make container-check`, раздел 4.

### 4.4. Настройки через переменные окружения (пункт 4)

Образ не содержит ни одной настройки среды: адрес базы, ключ подписи, пароли
передаются переменными при запуске. Источник — `.env.docker` (права 600, нет в
git и в образе), который `make docker-env` создаёт со случайными значениями.
В `docker-compose.yml` секреты только подставляются: `${POSTGRES_PASSWORD:?…}`
— без значения compose откажется запускать окружение.

### 4.5. Корректное завершение (пункт 5)

`docker stop` посылает процессу 1 сигнал SIGTERM. Чтобы его получил сервер,
а не оболочка, `entrypoint.sh` заменяет себя на `uvicorn` через `exec`.
Получив сигнал, uvicorn перестаёт принимать соединения, до 10 секунд ждёт
текущие запросы и вызывает завершение приложения — оно закрывает пул
соединений с базой и пишет в журнал «AudFond остановлен». У Docker на это
`stop_grace_period: 15s`; если не уложиться, процесс будет убит SIGKILL с кодом
137. PostgreSQL останавливается по SIGINT (быстрая остановка с записью на
диск), ему отведено 30 секунд.

Проверка: `make shutdown-drill` — код выхода 0 и записи в журнале.

### 4.6. Compose, сеть, том, healthcheck, порядок запуска (пункты 6–7)

- Том `audfond_db-data` с явным именем: данные отделены от контейнера.
- Healthcheck: у базы — `pg_isready`, у приложения — `/healthz` (объявлен в
  образе), у Nginx — `/nginx-health`.
- Порядок: `db` healthy → `migrate` завершилась успешно
  (`service_completed_successfully`) → `app1`, `app2` healthy → `nginx`.
  `make up` ждёт, пока все станут здоровыми (`--wait`).

Миграции вынесены в отдельную одноразовую службу: при двух экземплярах каждый
накатывал бы их сам, наперегонки.

### 4.7. Порт базы (пункт 8)

У `db` нет `ports`. Доступ — только из сети `backend`. Для отладки:
`docker compose --env-file .env.docker exec db psql -U audfond`.

### 4.8. Сохранность данных (пункт 9)

`make persist-drill`: пишет метку в базу, пересоздаёт все контейнеры
(`--force-recreate`), затем пересобирает образ с новым коммитом и запускает
окружение на нём. Метка на месте, том тот же (дата создания не изменилась).

### 4.9. Миграции, копия и восстановление в контейнерах (пункт 10)

| Действие | Команда | Как сделано |
|---|---|---|
| миграции | `make migrate` | `docker compose run --rm migrate` |
| копия | `make backup` | `pg_dump` внутри контейнера `db`: версия совпадает с сервером, порт не нужен; файл ложится на машину в `backups/` |
| восстановление | `make restore FILE=…` | экземпляры приложения останавливаются, `pg_restore --clean` внутри `db`, экземпляры запускаются и проверяются |
| в новый том | `make restore-new-volume FILE=…` | окружение снимается, база поднимается на новом пустом томе, копия разворачивается, окружение запускается поверх; старый том не трогается |
| учения | `make restore-drill`, `make migrate-drill` | те же учения ЛР3, в контейнере `tests` |

### 4.10. Ресурсы (пункт 11)

Лимиты заданы по замерам `docker stats` на этом окружении: простой и загрузка
реестра на 2000 помещений через Nginx (17 секунд при лимите 0,5 CPU), и
затем с запасом.

| Служба | CPU | Память | Процессов | Замер: простой → пик | Обоснование |
|---|---|---|---|---|---|
| `app1`, `app2` | 0.50 | 384 МБ | 128 | 74 → 87 МБ | разбор XLSX до 20 МБ держит книгу в памяти; запас ×4 под крупный файл. 0,5 CPU: тяжёлая загрузка на одном экземпляре не отнимает процессор у второго и у базы |
| `db` | 1.00 | 512 МБ | 200 | 48 → 51 МБ | `shared_buffers` 128 МБ, рабочая память запросов и `pg_dump` внутри контейнера; процессы — до 100 соединений плюс служебные |
| `migrate` | 0.50 | 256 МБ | 64 | — | одноразовая, только Alembic |
| `nginx` | 0.25 | 64 МБ | 64 | 3 → 4 МБ | проксирование, буферы запросов |

Сумма лимитов памяти долгоживущих служб — 1,3 ГБ, фактически занято около
250 МБ: лимит — это потолок на случай ошибки, а не резерв. Лимит числа
процессов защищает машину от «вилочной бомбы» в контейнере.

## 5. Проверка окружения (пункты 12–14)

`make container-check` — см. CONTRIBUTING.md, раздел 3.4. Проверяет файлы,
образ и работающие контейнеры; при любом нарушении код возврата 1 и окружение
не принимается. `make up` выполняет её до запуска: непроверенное изменение
окружения до контейнеров не доходит (пункт 14).

## 6. Nginx и масштабирование (дополнительное задание)

| Пункт | Как сделано |
|---|---|
| 1. Nginx отдельным контейнером | служба `nginx`, образ без root |
| 2. Нет прямого доступа к приложению | у `app1` и `app2` нет `ports`; снаружи доступен только порт Nginx |
| 3. Не менее двух экземпляров | `app1` и `app2` из одного образа |
| 4. Распределение запросов | `upstream` по кругу (round robin), соединения к экземплярам переиспользуются (`keepalive`) |
| 5. Идентификатор экземпляра | заголовок `X-Instance` в каждом ответе, поле `instance` в `/healthz` и `/version`; Nginx добавляет `X-Upstream` с адресом узла |
| 6. Отказ одного экземпляра | `make failover-drill`: после остановки `app2` все запросы успешны |
| 7. Отказоустойчивость | исключение узла (`max_fails=2 fail_timeout=10s`), повтор на другом узле (`proxy_next_upstream`, только для безопасных методов — POST загрузки не повторяется), ограничение частоты входа: 10 попыток в минуту с одного адреса, подряд — не больше 6 (`limit_req` с `burst=5`), сверх — ответ 429 |

### 6.1. Что мешает горизонтальному масштабированию (пункт 8)

Найдено при запуске двух экземпляров; что уже исправлено — отмечено.

1. **Миграции при запуске.** Каждый экземпляр накатывал бы схему сам, и
   несколько одновременных `alembic upgrade` конфликтуют. *Исправлено:*
   отдельная служба `migrate`, экземпляры её ждут.
2. **Долгая синхронная загрузка реестра.** Обработчик загрузки был
   асинхронным, а разбор файла — синхронным: на время загрузки экземпляр
   переставал отвечать совсем, включая healthcheck, и помечался нездоровым.
   *Исправлено:* разбор вынесен в пул потоков. Остаётся то, что загрузка
   выполняется внутри запроса: большой файл занимает поток и соединение с
   базой на минуты, а Nginx ждёт ответа до 300 секунд. Правильное решение —
   очередь фоновых задач и отдельный обработчик.
3. **Одна база.** Все экземпляры пишут в один PostgreSQL: он — единая точка
   отказа и предел роста записи. Масштабируются только экземпляры приложения.
4. **Пул соединений на каждый экземпляр.** До 10 соединений
   (`pool_size=5`, `max_overflow=5`) на экземпляр при `max_connections=100`:
   больше девяти экземпляров база не примет. Нужен пул перед базой (PgBouncer).
5. **Счётчик неудачных входов.** Хранится в базе, поэтому общий для всех
   экземпляров, но увеличивается как «прочитать — прибавить — записать» без
   блокировки строки: одновременные попытки на разных экземплярах могут
   потерять часть увеличений. Подбор пароля дополнительно сдерживает Nginx.
6. **Ограничение частоты в Nginx — в памяти Nginx.** При нескольких
   балансировщиках счётчики у каждого свои.
7. **Состав узлов записан в конфигурации Nginx.** Адреса экземпляров
   постоянные; третий экземпляр требует правки `default.conf`, а
   `docker compose --scale` здесь неприменим. Нужен динамический поиск узлов
   (оркестратор или `resolve` в upstream).
8. **Общий ключ подписи.** Токен, выданный одним экземпляром, принимается
   другим только при одинаковом `JWT_SECRET` — он задаётся одной переменной для
   всех экземпляров.

Что масштабированию не мешает: вход по токену без серверных сессий, журналы
в стандартный вывод с идентификатором запроса (его передаёт Nginx), файловая
система экземпляров только для чтения — состояния на диске экземпляра нет.

## 8. Анализ образа на уязвимости (ЛР5)

```bash
make build        # собрать образ
make image-scan   # проверить его
```

`scripts/image_scan.py` проверяет образ приложения `audfond:0.5.0` — тот, что
работает в бою и публикуется. Ищутся известные уязвимости в пакетах системы
(Debian) и в пакетах Python внутри образа. Сканер — Trivy.

| Решение | Почему |
|---|---|
| Trivy в контейнере, версия `aquasec/trivy:0.72.0` закреплена точно | в марте 2026 года выпуски Trivy и тег `latest` были скомпрометированы: плавающий тег у инструмента безопасности особенно опасен |
| образ передаётся сканеру файлом (`docker image save`), только для чтения | сканеру не нужен `docker.sock`, а доступ к нему равен root на машине |
| сканер работает от пользователя, запустившего проверку, без возможностей ядра | то же требование, что к контейнерам приложения |
| порог — HIGH и CRITICAL, для которых выпущено исправление | такую уязвимость можно и нужно закрыть обновлением; без исправления — видна в отчёте с ключом `--all`, но не блокирует |
| кэш базы уязвимостей — `~/.cache/audfond-trivy` | без кэша каждый запуск заново скачивает базу |

Отчёт — `reports/trivy.json`. Коды возврата: 0 — чисто, 1 — находки или
нарушен порядок исключений, 2 — проверка не выполнена (нет образа, Docker или
базы уязвимостей). Как и у проверки зависимостей, «не удалось проверить» — тоже
отказ.

**Базу уязвимостей** Trivy скачивает с `mirror.gcr.io`, при недоступности — с
`ghcr.io`. Если с машины недоступны оба, зеркало задаётся переменной окружения:
`TRIVY_DB_REPOSITORY=<адрес зеркала> make image-scan` — все переменные
`TRIVY_*` передаются сканеру.

**Исключения** — файл `.trivyignore.yaml`. У каждой записи обязательны причина
(`statement`) и срок пересмотра (`expired_at`): бессрочное исключение
превращается в забытое. Запись без причины или со сроком в прошлом — отказ
проверки. Добавляется только с обоснованием в запросе на слияние (ТЗ 7.2).

**Если сканер нашёл уязвимости**, почти всегда причина — устаревший базовый
образ: в выпуске ветки 3.12 от декабря 2024 года в пакетах Debian накопились
уязвимости, исправленные позже. Лечится обновлением `ARG PYTHON_IMAGE` в
`docker/Dockerfile` до свежего выпуска и пересборкой, а не исключением.

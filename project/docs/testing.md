# Тесты и локальный проверочный контур

Программный документ к этапу 3 (ЛР №3). Основание: ТЗ **А.В.00001-01 33 01-1**,
подразделы 7.1 и 7.2.

Любое изменение подчиняется одному контуру проверок, запускаемому одной
командой. Контур одинаков локально и в CI — это требование подраздела 7.1 ТЗ.

```bash
make verify
```

Способ запуска выбирается сам: в контейнерах — если Docker запущен и создан
`.env.docker` (`make docker-env`), иначе в локальном окружении `.venv`. Принудительно —
`make LOCAL=1 verify` (без контейнеров) или `make LOCAL=0 verify`
(в контейнерах). Текущий способ показывает `make mode`.

**`make verify` не трогает боевую базу.** Обратимость миграций проверяется на
одноразовой базе, которая создаётся и удаляется: `downgrade base` на рабочей
базе снёс бы все данные.

---

## 1. Из чего состоит `make verify`

Порядок не случайный: сначала дешёвые проверки, которые падают за секунды,
потом дорогие. Нет смысла прогонять тесты на базе, если код не форматирован.

| Шаг | Команда | Что проверяет | Чем падает |
|---|---|---|---|
| 1 | `make quality` | `ruff check` и `ruff format --check` | нарушение стиля, неиспользуемый импорт, неотформатированный файл |
| 2 | `make types` | `mypy app scripts` | несовпадение типов, обращение к несуществующему полю |
| 3 | `make sast` | `bandit` по `app` и `scripts` | небезопасные конструкции: подстановка в SQL, слабый хэш, открытый порт |
| 4 | `make secrets` | `scripts/secret_scan.py` | пароль или ключ, записанный строкой; запрещённый файл в репозитории |
| 5 | `make waivers` | `scripts/waiver_check.py` | подавление анализатора без обоснования, снижение порога покрытия |
| 6 | `make migrate-check` | обратимость миграций на одноразовой базе | миграция без рабочего `downgrade` |
| 7 | `make test` | весь набор тестов на настоящем PostgreSQL | любое нарушение поведения |

Отдельно, не в составе `verify`, потому что требуют отдельной базы или заметно
дольше идут:

| Команда | Что делает |
|---|---|
| `make test-report` | те же тесты + отчёты `reports/junit.xml`, `reports/coverage.xml`, `reports/htmlcov/` |
| `make coverage-services` | отдельный порог покрытия сервисного слоя — 80% (ТЗ 7.1) |
| `make mutants` | мутационная проверка правил (раздел 4) |
| `make migrate-drill` | учения по миграциям: чистая база и база с данными (раздел 5) |
| `make restore-drill` | учения по восстановлению из копии (раздел 6) |
| `make guard` | защита файлов приёмки: удалённые тесты и ослабленные проверки относительно `main` (раздел 12) |
| `make secrets-branch` | секреты во всех коммитах ветки, включая удалённые позже (раздел 11); нужен git |
| `make deps-check` | зависимости из `requirements.lock` и `requirements-dev.lock` — на известные уязвимости (раздел 10); нужен доступ к pypi.org |

## 2. Почему тесты идут на настоящем PostgreSQL

Половина правил предметной области живёт в схеме, а не в коде:

- объём помещения считает база вычисляемым столбцом
  `GENERATED ALWAYS AS (seats + staff_seats) STORED`;
- уникальность номера внутри корпуса — ограничение `uq_room_building_number`;
- запрет нулевого этажа и неположительной площади — ограничения `CHECK`;
- типы перечислений (`user_role`, `import_status`) существуют только в
  PostgreSQL.

На SQLite ничего из этого не воспроизводится, и тесты проверяли бы не то
приложение, которое потом развернут. Поэтому набор тестов требует живой базы и
на её отсутствие отвечает пропуском с внятным сообщением, а не выдумывает
замену.

## 3. Изоляция тестовых данных

Требование пункта 6 задания — отдельная тестовая конфигурация и изоляция
данных. Устроено так:

- **своя база на каждый прогон.** `tests/conftest.py` создаёт базу с именем
  `audfond_test_<случайные символы>`, накатывает на неё миграции тем же
  `alembic upgrade head`, что и в бою, и удаляет её после прогона. Прогоны не
  мешают друг другу и не оставляют следов;
- **схема накатывается миграциями, а не `create_all`.** Иначе тесты проверяли
  бы схему, которой в бою не будет;
- **откат после каждого теста.** Каждый тест работает в транзакции, которая
  отменяется: соседние тесты не видят чужих записей;
- **отдельная конфигурация.** `APP_ENV=test`, свой ключ подписи, уровень
  журнала `WARNING`. Боевые настройки в тестах не используются;
- **адрес базы для тестов** задаётся переменной `TEST_ADMIN_DSN` и отличается
  от `DATABASE_URL` приложения: роль приложения не имеет права создавать базы
  (подраздел 4.4 ТЗ), и это тоже проверяется самим фактом разделения.

## 4. Мутационное тестирование

Пункт 5 задания: на защите преподаватель меняет одно условие в основной логике,
и тесты обязаны это заметить. Проверять это надо заранее, иначе на защите
выяснится, что правило не покрыто.

```bash
make mutants                                 # весь набор
python scripts/mutation_check.py --list      # перечень мутаций
python scripts/mutation_check.py --only D5   # одно правило
```

Сценарий сам портит условие в коде, прогоняет связанные тесты и требует, чтобы
они упали. Мутация, после которой тесты зелёные, называется **выжившей** — это
прямое доказательство, что правило не проверяется.

Набор из восьми подмен:

| Правило | Подмена | Что перестаёт работать |
|---|---|---|
| D5 | `total > capacity` → `total > capacity + 1` | норма вместимости не срабатывает ровно на границе |
| D5 | округление вниз → округление вверх | остаток площади «добавляет» место |
| D6 | снят фильтр пригодности | в подбор попадают непригодные помещения |
| D1 | снята проверка матрицы допустимости | дисциплину можно вести в неразрешённом типе |
| D2 | `margin < 0` → `margin < -1` | перегруз на одного человека проходит без разрешения |
| Импорт | `number <= 0` → `number < 0` | площадь 0 проходит разбор |
| Импорт | сухой прогон начинает писать в базу | проверка файла перестаёт быть проверкой |
| Импорт | отказ по строке отменяет весь файл | теряется частичное сохранение |

Набор свой, а не сгенерированный, сознательно: генератор даёт тысячи мутантов,
из которых большая часть бессмысленна (меняется текст сообщения, порядок полей
в ответе), прогон занимает десятки минут, а выживших приходится разбирать
по одному. Здесь каждая подмена названа словами и прогоняется за секунды.

**Этот набор уже принёс пользу.** При первом прогоне две мутации выжили:
не было ни одного теста с площадью, которая не делится на норму без остатка
(D5), и ни одного с группой ровно на одного человека больше числа мест (D2).
Оба случая дописаны в `tests/unit/test_rule_d5.py` и
`tests/integration/test_selection.py`.

## 5. Учения по миграциям

Пункт 9 задания: проверить создание чистой базы и обновление базы, уже
содержащей данные.

```bash
ADMIN_DATABASE_URL=postgresql://postgres@localhost:5432/postgres make migrate-drill
```

Три части, и третья важнее первых двух:

1. **Чистая база.** Накат с нуля до последней ревизии, затем `alembic check`:
   схема обязана совпадать с моделями. Ловит ситуацию «модель поменяли,
   миграцию забыли».
2. **Полный откат и повторный накат.** Требование подраздела 4.6 ТЗ. Отдельно
   проверяется, что после откатa не осталось ни таблиц, ни типов перечислений:
   перечисления PostgreSQL живут отдельно от таблиц, и забытый `DROP TYPE`
   ломает повторный накат с «type already exists».
3. **База с данными.** Схема поднимается до состояния предыдущего этапа,
   заполняется, и только потом накатываются новые миграции. Сверяется, что
   число записей и суммарный объём не изменились. Ловит миграцию, которая на
   пустой базе проходит, а на заполненной теряет данные — например столбец
   `NOT NULL` без значения по умолчанию.

Именно поэтому миграция `0005_room_import_source` добавляет
`room.import_job_id` как `nullable` и без значения по умолчанию: накат на
заполненную таблицу не перезаписывает строки и не держит долгую блокировку.
У помещений, заведённых вручную, значение остаётся пустым — и это верный
ответ на вопрос «каким импортом заведено», а не ноль и не заглушка.

Обе базы учений временные, создаются и удаляются сценарием. Боевую базу он не
трогает.

## 6. Учения по восстановлению

Пункты 11 и 12 задания. Резервная копия, которую ни разу не разворачивали,
копией не считается.

```bash
ADMIN_DATABASE_URL=postgresql://postgres@localhost:5432/postgres make restore-drill
```

Сценарий проходит весь путь на тех же командах, что и в бою:

1. поднимает одноразовую базу и заполняет известными данными, запоминая число
   записей, суммарный объём и контрольную сумму `md5` по всем помещениям;
2. снимает копию через `scripts/backup.sh` (`pg_dump -Fc`), проверяя, что файл
   читается `pg_restore --list` — битая копия обнаруживается сразу, а не в день,
   когда она понадобится;
3. **портит данные двумя способами**: удаляет строки и подменяет значения.
   Второй опаснее: база остаётся работоспособной, а данные неверны;
4. убеждается, что порча действительно состоялась — иначе учения бессмысленны;
5. восстанавливает через `scripts/restore.sh` (`pg_restore --clean --if-exists`);
6. сверяет всё до контрольной суммы и проверяет, что схема по-прежнему
   совпадает с моделями.

## 7. Запреты

Подраздел 7.2 ТЗ и пункт 14 задания запрещают «удаление или пропуск тестов,
отключение анализаторов, снижение порогов качества и добавление исключений без
обоснования». Запрет не только записан словами, но и проверяется:

```bash
make waivers
```

`scripts/waiver_check.py` требует, чтобы рядом с каждым подавлением
(`# noqa`, `# type: ignore`, `# nosec`, `# pragma: no cover`) была причина
по-русски, чтобы пропущенный тест нёс текст причины, и чтобы порог покрытия в
`pyproject.toml` не был ниже значения из ТЗ. Порог продублирован в самом
сценарии: снизить его одной правкой не получится, придётся менять и настройку,
и проверку — то есть сделать это заметно в запросе на слияние.

**Подавление не запрещено, запрещено молчаливое подавление.** Иногда анализатор
ошибается: `computed_field` в Pydantic возвращает `property`, а `mypy` ждёт
метод, и подавление здесь честнее переписывания кода под анализатор. Но через
месяц никто не вспомнит, почему оно там, если не написать причину в той же
строке.

Замечание bandit о привязке к `0.0.0.0` закрыто не подавлением, а изменением
поведения: значение `APP_HOST` по умолчанию теперь `127.0.0.1`, а открытие всех
интерфейсов стало осознанным решением среды развёртывания и задано явно в
`docker-compose.yml` и в `audfond.env`.

## 9. На что смотреть в первую очередь

Три места, которые спрашивают всегда:

- **правило D5** (`app/services/rooms.py`, `app/models/room_type.py`) — почему
  проверка живёт в сервисном слое, а не ограничением базы: норма лежит в другой
  таблице, а `CHECK` в PostgreSQL не умеет обращаться к другим таблицам;
- **частичное сохранение при импорте** (`app/services/imports.py`) — почему
  каждая строка пишется в своей точке сохранения `SAVEPOINT`: без этого первая
  же ошибка уровня базы испортила бы сессию и пришлось бы отменять весь файл;
- **формат ошибки** (`app/errors.py`) — почему у любого отказа есть код и
  `request_id` и почему наружу не уходит ни трассировка, ни текст SQL.

## 10. Проверка зависимостей

ЛР5, пункт 12. Код проекта может быть безупречным, а уязвимость придёт с
библиотекой. Поэтому закреплённые версии из lock-файлов сверяются с базой
известных уязвимостей:

```bash
make deps-check
```

Инструмент — `pip-audit` (закреплён в `requirements-dev.txt`), база —
PyPI/OSV. Проверяются ровно те версии и контрольные суммы, что записаны в
`requirements.lock` и `requirements-dev.lock`: ничего не устанавливается и не
разрешается заново. Отчёт — `reports/pip-audit.json`.

| Код возврата | Значение |
|---|---|
| 0 | известных уязвимостей нет |
| 1 | найдены уязвимости: пакет, версия, идентификатор и версия с исправлением |
| 2 | проверка не выполнена: нет доступа к базе уязвимостей |

Код 2 — тоже отказ. «Не удалось узнать» не означает «уязвимостей нет», и
пропустить такую проверку молча было бы ослаблением.

В контейнерном режиме проверка идёт в образе проверок, но не в службе `tests`:
та работает во внутренней сети без выхода наружу, а базе уязвимостей нужен
pypi.org. Дерево проекта подключается только для чтения, поэтому проверяются
текущие lock-файлы, а не те, что были при сборке образа.

**Исключения.** Если уязвимость не касается проекта (например, затронута
функция, которую он не вызывает), её идентификатор с причиной вносится в
словарь `ALLOWED` в `scripts/deps_check.py`. Только с обоснованием в запросе на
слияние — так же, как исключения поиска секретов (ТЗ 7.2).

## 11. Секреты в коммитах ветки

`make secrets` смотрит текущее дерево. Этого мало: пароль, добавленный одним
коммитом и удалённый следующим, в дереве уже не виден, но в истории остаётся
навсегда — любой, у кого есть клон, найдёт его в `git log -p`. Поэтому ветка
проверяется целиком:

```bash
make secrets-branch                 # с чем сравнивать — origin/main
make secrets-branch BASE=main       # или любая другая ветка
```

Сценарий тот же — `scripts/secret_scan.py`, с ключом `--since`: берётся
общий предок ветки с `BASE`, и каждая добавленная строка каждого коммита после
него проверяется теми же правилами, что и дерево. Новый файл проверяется и по
имени: `.env`, дамп, закрытый ключ. Отчёт — `reports/secrets-branch.json`.

Проверка идёт на машине, а не в контейнере: ей нужен git с историей, а в образ
проверок `.git` не копируется. По той же причине и `make secrets` теперь
запускается на машине в любом режиме: он смотрит файлы репозитория
(`git ls-files`), а в образе проверок лежит копия дерева на момент сборки —
новый файл с паролем туда не попал бы, пока образ не пересобран.

Найденный в ветке секрет считается раскрытым: его надо сменить, а ветку
исправить до слияния — в `main` такой коммит попасть не должен.

**Исправлено в том же сценарии.** Правило «имя = значение в кавычках» искало
имя по границе слова, а после подчёркивания граница не срабатывает: строка
`SMTP_PASSWORD = "…"` проходила незамеченной, ловилось только голое
`password = "…"`. Теперь имя может нести приставку (`DB_`, `SMTP_`, `github_`),
а значение, начинающееся с `$`, считается подстановкой переменной оболочки.

## 12. Защита файлов приёмки

ЛР5, пункты 13–15. Раздел 7 запрещает молчаливые подавления, но не видит
другого: удалённого теста, теста без проверок, шага, убранного из
`make verify`. Для этого нужно сравнение с тем, что уже принято:

```bash
make guard                 # ветка против origin/main
make guard BASE=main
```

`scripts/acceptance_guard.py` берёт общий предок ветки с `BASE` и сравнивает:

- **тесты** — по синтаксическому дереву, а не по тексту: для каждой функции
  `test_*` считается число проверок (`assert`, `pytest.raises`) и случаев
  `parametrize`. Тест пропал, проверок или случаев стало меньше, появился
  пропуск — ослабление. Переименованный файл отслеживается;
- **Makefile** — состав `make verify`, наличие целей проверок, подавления
  ошибок в их командах;
- **pyproject.toml** — правила ruff, строгость mypy, исключения bandit и
  покрытия, порог покрытия, настройки сбора тестов;
- **сценарии проверок** — словари исключений, порог в `waiver_check.py`,
  число проверок в `container_check.py`, записи `.trivyignore.yaml`.

Отчёт — `reports/guard.md`: число тестов до и после, найденные ослабления,
изменённые критические файлы. Его удобно прикладывать к запросу на слияние.

**Почему запускается версия из `main`.** Если бы проверка шла в редакции
ветки, достаточно было бы в той же ветке научить её ничего не находить. Поэтому
`make guard` достаёт сценарий из `BASE` (`git show`) и запускает его; версия из
ветки идёт только при первом появлении сценария.

**Обоснованное ослабление** не запрещено, запрещено незаметное: строка
`Обоснование-ослабления: …` в сообщении коммита пропускает проверку, но каждое
ослабление остаётся в отчёте, и решение принимает ответственный за
критические файлы.

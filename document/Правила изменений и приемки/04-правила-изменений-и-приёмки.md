# Правила внесения и приёмки изменений

Программный документ по разделу 5 ТЗ **А.В.00001-01 33 01-1**;
порядок контроля — раздел 7 ТЗ.

Любое изменение кода, документации или конфигурации считается потенциально
ошибочным **независимо от источника**: написано оно руками или получено
средствами ИИ. Включение в ветку `main` допускается только после полного цикла
проверок.

## 2. Порядок работы над изменением

### 2.1. Задача

Каждое изменение начинается с задачи (Issue). Её номер указывается **в трёх
местах**: в имени ветки, в сообщении коммита и в запросе на слияние.

### 2.2. Ветка

Работа ведётся только в отдельной тематической ветке. **Прямой push в `main`
запрещён.**

```
feat/<номер>-<кратко>     новая функция
fix/<номер>-<кратко>      исправление
docs/<номер>-<кратко>     документация
chore/<номер>-<кратко>    служебное
```

### 2.3. Локальная проверка

До отправки изменение обязано пройти проверки на машине разработчика **одной
командой**:

```bash
make verify
```

Состав — в разделе 3. В CI выполняются те же команды, что и локально.

### 2.4. Коммиты

Стандарт **Conventional Commits**:

```
feat(rooms): карточки помещений и ключевое правило D5 (#9)

Тело: что и почему сделано, какие правила затронуты.

Refs #9
```

Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`.
Область в скобках — затронутый раздел (`rooms`, `auth`, `schema`, `deploy`).

### 2.5. Синхронизация

Рабочая ветка подтягивает актуальный `main` методом **rebase**, не merge:
история остаётся линейной.

```bash
git fetch origin
git rebase origin/main
```

### 2.6. Запрос на слияние

Заголовок совпадает с заголовком задачи. Тело начинается строкой
`Closes #<номер>` — тогда задача закроется автоматически при слиянии.
В теле указывается, что смотреть ревьюеру и как проверить изменение.

### 2.7. Ревью

Смотрит **не автор**. Формальное «lgtm» не считается ревью: ревьюер задаёт
вопрос по существу либо указывает на конкретное место. Одобрение ставится
кнопкой **Approve**.

### 2.8. Слияние

**Squash and Merge** в `main` — только при зелёных проверках и одобрении
ревьюера.

### 2.9. Версия

Результат этапа фиксируется **аннотированным** тегом по правилам
семантического версионирования:

```bash
git tag -a v0.1.0 -m "Минимальная версия по ТЗ, этап 1"
git push origin v0.1.0
```

Для каждой версии прослеживается путь: задача → ветка → коммиты → запрос на
слияние → проверки → тег.

## 3. Обязательные команды проверки

Единый командный интерфейс (ТЗ 7.1). Полный список — `make help`.

### 3.1. Перед каждым запросом на слияние

```bash
make verify
```

Выполняет по порядку:

| Шаг | Команда | Что проверяет |
|---|---|---|
| 1 | `make quality` | линтер `ruff check` и форматирование `ruff format --check` |
| 2 | `make types` | проверка типов `mypy app` |
| 3 | `make migrate-check` | обратимость миграций: `upgrade → downgrade → upgrade`, затем `alembic check` |
| 4 | `make test` | весь набор тестов на настоящем PostgreSQL |

Если хоть один шаг красный — запрос на слияние не открывается.

### 3.2. Отдельные команды

| Команда | Что делает |
|---|---|
| `make up` / `make down` | поднять / остановить приложение и базу в контейнерах |
| `make setup` / `make run` | окружение и запуск без контейнеров |
| `make migrate` | накатить миграции |
| `make create-admin` | создать первого администратора (логин и пароль из `.env`) |
| `make seed` | демонстрационные данные |
| `make test` | тесты в контейнере |
| `make test-cov` | тесты с отчётом о покрытии |
| `make quality` | линтер и форматирование |
| `make types` | проверка типов |
| `make container-check` | образ по требованиям 4.5 ТЗ |
| `make backup` | резервная копия базы в `backups/` |
| `make restore FILE=…` | восстановление из копии |
| `make logs` / `make ps` | журнал и состояние служб |
| `make clean` | снести контейнеры вместе с данными базы |

### 3.3. Пороги качества

| Показатель | Порог по ТЗ 7.1 | Фактически в v0.1.0 |
|---|---|---|
| покрытие тестами, общее | не менее 70% | 91% |
| покрытие сервисного слоя | не менее 80% | выше 90% |
| линтер, типы | без ошибок | без ошибок |
| обратимость миграций | обязательна | проверяется `make migrate-check` |

### 3.4. Проверка образа

```bash
make container-check
```

Проверяет требования подразделов 4.5 и 7.2 ТЗ: процесс не от `root`, тег
`latest` не используется, объявлен `healthcheck`, порт СУБД наружу не
публикуется, в переменных образа нет секретов.

### 3.5. Проверка восстановления

Резервная копия, которую ни разу не разворачивали, — это не копия. Порядок:

```bash
make backup                                   # снять копию
# удалить или изменить тестовую запись
make restore FILE=backups/audfond-…​.dump      # восстановить
# убедиться, что запись вернулась
```

## 4. Требования к самому изменению

- Правила предметной области проверяются **в сервисном слое**, а не в
  обработчике и не в шаблоне: один источник истины для API и веб-интерфейса.
- Новое правило или новая ветка логики приходит **вместе с тестом**.
- Изменение схемы базы — **только миграцией Alembic**, с рабочим `downgrade`.
- Документация правится **в том же запросе на слияние**, что и код, к которому
  относится.
- Ответ об ошибке содержит код, сообщение по-русски и `request_id`.
  Трассировка стека и текст SQL наружу не уходят.
- Версии зависимостей закреплены точно (`==`). Проверять изменение надо на
  **закреплённых** версиях: более свежая библиотека прощает то, на чём упадёт
  контейнер.

## 5. Запрещённые действия

Подраздел 7.2 ТЗ.

| Запрещено | Почему |
|---|---|
| прямой push в `main` и `git push --force` в `main` | ломает историю и обходит проверки |
| размещать в репозитории секреты, `.env`, локальные файлы окружения, резервные копии, артефакты сборки | утечка учётных данных |
| удалять или пропускать тесты, отключать анализаторы, снижать пороги качества без обоснования в запросе на слияние | обесценивает проверки |
| ослаблять проверки CI ради прохождения конвейера | то же |
| менять схему базы вручную SQL-скриптами в обход Alembic | схема расходится с миграциями, обновление ломается |
| использовать тег `latest` для образов | сборка перестаёт быть воспроизводимой |
| запускать контейнеры от `root` | нарушение требований 4.5 ТЗ |
| публиковать лишние порты, включая порт СУБД | расширение поверхности атаки |
| писать пароли и токены в журнал | нарушение 4.5 и 4.6 ТЗ |

## 6. Порядок приёмки

Подраздел 7.4 ТЗ. Приёмка этапа проводится на защите лабораторной работы.

### 6.1. Что предъявляется

1. **Живая демонстрация функций этапа** — на развёрнутом приложении, не на
   скриншотах.
2. **Успешное выполнение `make verify`** — при комиссии.
3. **Отсутствие секретов и локальных файлов в репозитории** — `.env` в
   `.gitignore`, в истории его нет.
4. **Внесение контрольного изменения** через задачу, ветку и запрос на
   слияние — прямо на защите.

### 6.2. Демонстрация для этапа 1

| Что показать | Как |
|---|---|
| приложение поднимается одной командой | `make up`, затем `/readyz` отвечает 200 |
| вход в систему и разграничение прав | войти администратором, затем наблюдателем: кнопок изменения нет, API отвечает 403 |
| каталог аудиторного фонда | пройти «корпус → этаж → помещение», открыть карточку |
| **ключевое правило D5** | попытаться внести обмер 30 м² при 24 местах — отказ с расчётом норматива |
| правила D1, D2, D6 при подборе | подобрать аудиторию: показать, сколько помещений отсеяло каждое правило |
| история обмеров | внести обмер, показать, что прежняя запись осталась |
| единый формат ошибки | любой отказ: код, сообщение, `request_id`, тот же в заголовке `X-Request-Id` |
| служебные адреса | `/healthz`, `/readyz`, `/version` |
| обратимость миграций | `make migrate-check` |
| требования к образу | `make container-check` |
| git-процесс | задачи, ветки, запросы на слияние, тег `v0.1.0` |

### 6.3. Критерий приёмки

Этап считается принятым, если:

- все обязательные проверки раздела 3 пройдены;
- функции этапа работают в соответствии с ТЗ;
- в репозитории нет секретов и локальных файлов;
- контрольное изменение прошло полный путь задача → ветка → запрос на слияние
  → слияние.

### 6.4. Если проверка не пройдена

Изменение возвращается автору. Правка вносится **в ту же ветку** новым
коммитом — история ревью сохраняется. Запрос на слияние не закрывается и не
пересоздаётся.

При обнаружении критической ошибки уже в `main` выполняется откат (`Revert`) с
обязательным понижением версии миграции базы, если изменение её затрагивало.

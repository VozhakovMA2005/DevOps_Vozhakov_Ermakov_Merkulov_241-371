# Описание программы AudFond

Программный документ по разделу 5 ТЗ **А.В.00001-01 33 01-1**.
Версия программы v0.1.0 — этап 1 (ЛР №1).

---

## 1. Назначение

### 1.1. Что делает система

AudFond ведёт учёт аудиторного фонда университета и помогает подбирать
помещения под занятия. Система отвечает на четыре вопроса:

- **какие помещения есть** — где находятся, какой площади, на сколько человек,
  пригодны ли к эксплуатации;
- **за кем они закреплены** — какое подразделение отвечает за помещение;
- **как менялись их характеристики** — история обмеров площадей с датами и
  авторами;
- **куда можно поставить занятие** — какие аудитории подходят дисциплине по
  типу, вместимости и пригодности.

### 1.2. Зачем это нужно

Аудиторный фонд университета живёт в таблицах, которые ведут разные люди:
инженер обмерил помещение, диспетчер поставил туда группу, комиссия посчитала
площади. Пока данные разъезжаются, случаются три типовые ошибки:

- **занятие в неподходящем помещении** — лекция в лаборатории, физкультура в
  компьютерном классе;
- **перегруз** — в аудиторию на 24 места ставят группу из 30;
- **нарушение санитарной нормы** — мест больше, чем допускает площадь.

Система не даёт совершить ни одну из них: каждая проверяется правилом и
отклоняется с объяснением, а не «замечается потом».

### 1.3. Границы этапа 1

**Входит:** учётные записи и роли, справочники (подразделения, корпуса, типы
помещений, дисциплины), карточки помещений, история обмеров, матрица
допустимости, подбор аудитории, веб-интерфейс, HTTP API, служебные адреса.

**Не входит** (по разделу 6.4 ТЗ, вынесено в следующие этапы):

| Что | Этап |
|---|---|
| импорт реестров и списков обучающихся из XLSX | 3 (ЛР №3) |
| алгоритм распределения групп по временным слотам | 5 (ЛР №5) |
| аналитические отчёты и выгрузка в XLSX | 6 (ЛР №6) |
| метрики Prometheus, панели, оповещения | 8 (ЛР №8) |

Учебные группы, обучающиеся, требования нагрузки, временные слоты и журнал
импорта — сущности этих этапов, в схеме версии v0.1.0 их нет.

## 2. Пользователи

Подраздел 3.3 ТЗ. Роль хранится в учётной записи и определяет права на каждом
адресе API и на каждой странице.

| Роль | Кто это | Что делает | Права |
|---|---|---|---|
| `SYS_ADMIN` | администратор системы | ведёт учётные записи, доступ ко всему | чтение и запись, плюс раздел пользователей |
| `FUND_ADMIN` | инженер, заведующий корпусом | справочники, карточки помещений, обмеры | чтение и запись |
| `DISPATCHER` | сотрудник учебно-методического управления | дисциплины, матрица допустимости, подбор | чтение и запись |
| `OBSERVER` | преподаватель, заведующий кафедрой, комиссия | смотрит каталог и карточки | только чтение |
| `SERVICE` | смежная информационная система | забирает данные по API | только чтение |

Как это работает в коде:

- нет действительного токена — **401**, код `UNAUTHENTICATED`;
- токен есть, но роль не подходит — **403**, код `FORBIDDEN`, в деталях
  указана ваша роль и список допустимых;
- наблюдателю и внешней системе веб-интерфейс не показывает кнопок изменения
  данных, а API отвечает 403 на любую запись.

Регистрации в системе нет: первого администратора создаёт служебная команда
`docker compose run --rm app admin`, остальных заводит он.

## 3. Сценарии работы

Подраздел 3.4 ТЗ. Каждый сценарий описан так, как он проходит в готовой
системе, с указанием правил, которые могут его остановить.

### S1. Вход в систему

Пользователь вводит логин и пароль на странице входа. Система сверяет пароль с
хэшем Argon2id и выдаёт токен доступа: в вебе — в cookie с `HttpOnly` и
`SameSite`, для смежных систем — в теле ответа для заголовка `Authorization`.

Неизвестный логин и неверный пароль дают **одинаковый** ответ: иначе форма
входа превращается в справочник существующих учёток. После пяти неудачных
попыток подряд вход блокируется на 15 минут, и верный пароль в это время тоже
не пускает.

### S2. Завести корпус

Администратор фонда указывает код, название, адрес, число этажей, наличие
подвала и паспортную площадь. Код корпуса уникален.

Этажность задаёт диапазон допустимых этажей для помещений: от −1 при наличии
подвала до числа этажей. **Этаж 0 не используется никогда.**

### S3. Завести структуру подразделений

Диспетчер создаёт подразделения, при необходимости указывая вышестоящее:
институт → факультет → кафедра. Иерархия — дерево, циклы запрещены.

### S4. Вести справочник типов помещений

Тип помещения несёт **норму площади на одного человека** — от неё считается
правило D5. Учебным типам норма задана (лекционная 2.50 м², лаборатория
4.50 м², компьютерный класс 6.00 м²), служебным — нет, и тогда вместимость не
нормируется.

Начальные значения справочника приходят миграцией: без них нельзя завести ни
одного помещения.

### S5. Завести карточку помещения

Инженер указывает корпус, номер, этаж, тип, площадь, число мест для
обучающихся и для сотрудников, пригодность и, при необходимости,
подразделение.

Система проверяет: номер уникален внутри корпуса, этаж существует в этом
корпусе, площадь положительна, **мест не больше нормативной вместимости
(D5)**. Объём помещения считает база; прислать его нельзя.

Вместе с карточкой заводится первая запись истории обмеров — иначе в истории
появится разрыв, и неоткуда будет узнать, с чего помещение начиналось.

### S6. Пройти по каталогу

Пользователь открывает каталог, выбирает корпус, затем этаж, затем помещение.
На каждом шаге показана навигационная цепочка. В карточке помещения видно
площадь, места, объём, норматив D5, подразделение и всю историю обмеров.

Список помещений фильтруется по корпусу, этажу, типу, подразделению,
пригодности, диапазону площади и поиску по номеру; выдача постраничная.

### S7. Внести обмер

Инженер вносит новый обмер: площадь, места, дату, примечание. Система
проверяет правило D5 и переносит значения в карточку помещения — карточка
всегда показывает последний обмер.

**История не переписывается.** Ошибочный обмер исправляется новым обмером, а
не правкой старого; удалить запись истории нельзя. Помещение, у которого есть
история, тоже не удаляется.

### S8. Отметить помещение непригодным

Инженер снимает признак пригодности — например, на время ремонта. Помещение
остаётся в каталоге и в учёте площадей, но **в подбор не попадает (D6)**.

### S9. Вести дисциплины и матрицу допустимости

Диспетчер заводит дисциплину и отмечает типы помещений, в которых её разрешено
проводить. Это и есть **матрица допустимости** — основа правила D1.

Пустая матрица — законное состояние: она означает, что дисциплине пока нечего
подобрать, и подбор сообщает об этом прямо, а не возвращает пустой список
молча.

### S10. Подобрать аудиторию под занятие

Диспетчер указывает дисциплину, численность группы и, при необходимости,
корпус. Система отбирает помещения в порядке правил ТЗ: сначала отбрасывает
непригодные (D6), затем не разрешённые матрицей (D1), затем те, где не хватает
мест (D2).

Ответ показывает не только подходящие помещения, но и **сколько помещений
отсеяло каждое правило**: диспетчер должен понимать, что менять — матрицу,
численность или пригодность.

Перегруз вместимости допускается только при явно включённом параметре
«разрешить перегруз» и помечается в ответе, чтобы попал в отчёт.

### S11. Исправить ошибку в данных

Любую запись справочника можно поправить частично: присланные поля меняются,
остальные сохраняются. Удаление запрещено, если на запись ссылаются другие
данные — система называет, кто именно ссылается и сколько таких записей.

### S12. Управлять учётными записями

Администратор системы создаёт пользователей, меняет им роль и пароль,
блокирует. Себе самому сменить роль или заблокировать себя нельзя — иначе
система остаётся без администратора.

Пароль в ответах API не встречается ни в каком виде, включая хэш.

### S13. Проверить работоспособность

Служба эксплуатации запрашивает `/healthz` (приложение живо), `/readyz` (база
доступна и миграции накатаны), `/version` (версия и коммит). Эти три адреса
доступны без входа в систему.

## 4. Правила работы системы

Подраздел 4.1.4 ТЗ. Нарушение правила отклоняет операцию, а ответ содержит код
правила и причину отказа.

| Правило | Формулировка | Где проверяется | Код ошибки | Этап |
|---|---|---|---|---|
| **D1** | занятие по дисциплине можно назначить только в помещение разрешённого типа | `app/services/selection.py` | `D1_DISCIPLINE_NOT_ALLOWED` | 1 |
| **D2** | численность группы не больше числа посадочных мест | `app/services/selection.py` | `D2_SEATS_EXCEEDED` | 1 |
| D3 | в одном помещении в одном слоте не более одного занятия | — | — | 5 |
| D4 | у одной группы в одном слоте не более одного занятия | — | — | 5 |
| **D5** | сумма посадочных мест не больше нормативной вместимости | `app/services/rooms.py` | `D5_NORM_CAPACITY_EXCEEDED` | 1 |
| **D6** | непригодное помещение не участвует в подборе | `app/services/selection.py` | `D6_ROOM_NOT_USABLE` | 1 |

D3 и D4 относятся к распределению по временным слотам — это этап 5. Сущностей
слота и назначения в схеме этапа 1 ещё нет, поэтому правила не реализованы и
не имитируются.

### 4.1. D5 — ключевое правило этапа 1

**Нормативная вместимость** = рабочая площадь ÷ норма площади на одного
человека для типа помещения, **с округлением вниз**.

```
62.50 м² ÷ 2.50 м²/чел = 25 чел.
62.49 м² ÷ 2.50 м²/чел = 24 чел.   ← округление вниз, а не до ближайшего
100.00 м² ÷ 6.00 м²/чел = 16 чел.  ← 16.66 отбрасывается до 16
```

Суммарное число мест — для обучающихся **и** сотрудников — не должно превышать
эту величину.

**Почему это не ограничение базы.** Норма лежит в таблице `room_type`, а
проверяемые значения — в `room`. `CHECK` в PostgreSQL не умеет обращаться к
другой таблице, а триггер спрятал бы правило от того, кто читает код
приложения. Поэтому проверка живёт в сервисном слое, в одной функции
`check_rule_d5`, и вызывается из **всех трёх мест**, где данные могут
измениться:

1. заведение карточки помещения;
2. правка карточки — включая смену типа и уменьшение площади;
3. внесение обмера.

Третий пункт существенный: обмер — это тоже ввод данных, и через него правило
обойти нельзя.

**Когда правило не применяется.** Если у типа помещения норма не задана
(`area_norm = NULL`), вместимость не нормируется и проверка пропускается. Это
не дыра: норма установлена только для учебных помещений, служебным она не
нужна.

**Что видит пользователь:**

```json
{
  "error": {
    "code": "D5_NORM_CAPACITY_EXCEEDED",
    "message": "Нормативная вместимость помещения — 25 чел. (площадь 62.50 м² / норма 2.50 м² на человека), а мест указано 31",
    "details": {
      "rule": "D5",
      "room_type_code": "SEMINAR",
      "area": "62.50",
      "area_norm": "2.50",
      "normative_capacity": 25,
      "requested_total_seats": 31,
      "excess": 6
    }
  },
  "request_id": "0f1c8d2b4e6a…"
}
```

Отказ говорит не только «нельзя», но и насколько превышено и от чего считалось.

### 4.2. D1 — матрица допустимости

Связь «многие ко многим» между дисциплинами и типами помещений
(`discipline_room_type`). При подборе тип помещения должен присутствовать в
матрице дисциплины, иначе помещение отбрасывается.

### 4.3. D2 — вместимость при подборе

Мест для обучающихся должно хватить группе. Перегруз допускается только при
явном `allow_overload=true`; каждое такое помещение помечается в ответе
(`overloaded: true`, отрицательный `seats_margin`).

### 4.4. D6 — пригодность

Помещение с `is_usable = false` не рассматривается при подборе вообще. При
этом оно остаётся в каталоге и в учёте площадей: непригодное — не значит
несуществующее.

### 4.5. Правила целостности данных

Сверх правил предметной области система соблюдает ограничения, записанные в
подразделах 4.1.5 и 4.6 ТЗ:

| Правило | Как обеспечено |
|---|---|
| код корпуса, подразделения, типа и дисциплины уникален; номер помещения уникален внутри корпуса | `UNIQUE` в базе плюс понятное сообщение приложения |
| удалить запись, на которую ссылаются другие, нельзя | `ON DELETE RESTRICT` плюс проверка в приложении, которая называет, кто ссылается |
| иерархия подразделений — дерево | `CHECK` против прямого самородительства плюс обход цепочки вверх в приложении |
| этаж помещения существует в корпусе, этаж 0 не используется | `CHECK` в базе плюс проверка диапазона по этажности корпуса |
| объём помещения считает база | вычисляемый столбец `GENERATED ALWAYS AS (seats + staff_seats) STORED` |
| площади — десятичные числа фиксированной точности | `numeric(9,2)` в базе, строка с двумя знаками в JSON |
| история обмеров не удаляется | отказ `HISTORY_IMMUTABLE`; помещение с историей не удаляется |
| пароль хранится только как хэш | Argon2id с индивидуальной солью; в ответах API пароля нет |
| конфигурация только из переменных окружения | без `DATABASE_URL` и `JWT_SECRET` приложение не стартует |

### 4.6. Как система отказывает

Любой отказ уходит клиенту в одном формате:

```json
{"error": {"code": "…", "message": "…", "details": {…}}, "request_id": "…"}
```

Тот же идентификатор ставится в заголовок `X-Request-Id` и пишется в журнал:
пользователь называет его в обращении, и запись находится по одному слову.
Наружу не уходят ни трассировка стека, ни текст SQL, ни значения секретов.

Полный перечень кодов — в `api.md`.

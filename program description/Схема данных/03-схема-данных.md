# Схема данных

Программный документ по разделу 5 ТЗ **А.В.00001-01 33 01-1**.
СУБД PostgreSQL 17. Версия схемы — ревизия `0002_seed_reference`.

Схема ведётся только миграциями Alembic. Ручное изменение структуры или данных
в обход миграций и сервисного слоя запрещено (ТЗ 4.3.2 и 7.2).

---

## 1. Состав сущностей

Восемь таблиц по подразделу 4.1.5 ТЗ.

```
              app_user
                  │ measured_by
                  ↓
   building ──< room >── room_type ──< discipline_room_type >── discipline
       │         │  │         ↑
       │         │  │         └─ area_norm: норма площади на человека (D5)
       │         │  └──< room_measurement
       │         │
   department ───┘  (закрепление помещения за подразделением)
       └──< department   (иерархия: родитель — дети)
```

| Таблица | Что хранит | Записей в демонстрационном наборе |
|---|---|---|
| `app_user` | учётные записи и роли | 4 |
| `department` | подразделения с иерархией | 4 |
| `building` | корпуса | 2 |
| `room_type` | типы помещений с нормой площади | 7 |
| `room` | карточки помещений | 14 |
| `room_measurement` | история обмеров | 14 |
| `discipline` | учебные дисциплины | 5 |
| `discipline_room_type` | матрица допустимости | 11 |

## 2. Таблицы

### 2.1. `app_user` — учётные записи

Имя `app_user`, а не `user`: `user` — зарезервированное слово PostgreSQL.

| Поле | Тип | NULL | Примечание |
|---|---|---|---|
| `id` | integer | нет | первичный ключ |
| `username` | varchar(50) | нет | уникален |
| `full_name` | varchar(150) | нет | |
| `password_hash` | varchar(255) | нет | Argon2id, соль внутри строки хэша |
| `role` | `user_role` | нет | перечисление, см. ниже |
| `is_active` | boolean | нет | заблокированная запись не входит |
| `failed_attempts` | integer | нет | неудачных попыток входа подряд |
| `locked_until` | timestamptz | да | до какого момента вход закрыт |
| `last_login_at` | timestamptz | да | |
| `created_at`, `updated_at` | timestamptz | нет | ставит база |

Перечисление `user_role`: `SYS_ADMIN`, `FUND_ADMIN`, `DISPATCHER`, `OBSERVER`,
`SERVICE`.

Ограничения: `uq_app_user_username`, `ck_app_user_username_len`
(длина логина ≥ 3), `ck_app_user_attempts` (`failed_attempts >= 0`).

Отдельного поля для соли нет и не нужно: Argon2 кладёт соль внутрь строки
хэша. Пароль в открытом виде не хранится нигде.

### 2.2. `department` — подразделения

| Поле | Тип | NULL | Примечание |
|---|---|---|---|
| `id` | bigint | нет | |
| `code` | varchar(30) | нет | уникален |
| `name` | varchar(200) | нет | |
| `parent_id` | bigint → `department.id` | да | вышестоящее подразделение |
| `head_fio` | varchar(150) | да | |

Ограничения: `uq_department_code`, `ck_department_not_self_parent`
(`parent_id IS NULL OR parent_id <> id`), внешний ключ на себя с `RESTRICT`.

`CHECK` ловит только прямое самородительство. Цикл длиннее одного шага
(A → B → C → A) проверяет приложение, обходя цепочку вверх: выразить это
ограничением базы без рекурсивного триггера нельзя.

### 2.3. `building` — корпуса

| Поле | Тип | NULL | Примечание |
|---|---|---|---|
| `id` | bigint | нет | |
| `code` | varchar(20) | нет | уникален |
| `name` | varchar(200) | нет | |
| `address` | varchar(300) | нет | |
| `floors_count` | smallint | нет | 1…100 |
| `has_basement` | boolean | нет | разрешает этаж −1 |
| `passport_area` | numeric(12,2) | да | паспортная площадь здания, м² |

Ограничения: `uq_building_code`, `ck_building_floors`,
`ck_building_area_positive`.

Этажность задаёт диапазон допустимых этажей помещений. **Этаж 0 не
используется**: нумерация идёт −1 (подвал), 1, 2, …

### 2.4. `room_type` — типы помещений

| Поле | Тип | NULL | Примечание |
|---|---|---|---|
| `id` | bigint | нет | |
| `code` | varchar(30) | нет | уникален |
| `name` | varchar(150) | нет | |
| `area_norm` | numeric(6,2) | **да** | м² на одного человека |
| `is_teaching` | boolean | нет | учебный ли тип |
| `note` | varchar(300) | да | |

Ограничения: `uq_room_type_code`, `ck_room_type_norm_positive`.

`area_norm` — основа правила D5. `NULL` означает, что вместимость помещений
этого типа не нормируется: у служебных и вспомогательных помещений нормы нет.

Начальные значения приходят миграцией `0002_seed_reference`:

| Код | Название | Норма, м²/чел |
|---|---|---|
| `LECTURE` | Лекционная аудитория | 2.50 |
| `SEMINAR` | Семинарская аудитория | 2.50 |
| `LAB` | Лаборатория | 4.50 |
| `COMPUTER` | Компьютерный класс | 6.00 |
| `SPORT` | Спортивный зал | 4.00 |
| `OFFICE` | Служебное помещение | — |
| `UTILITY` | Вспомогательное помещение | — |

Справочник приезжает миграцией, а не заполняется руками после развёртывания:
без него нельзя завести ни одного помещения.

### 2.5. `room` — помещения

| Поле | Тип | NULL | Примечание |
|---|---|---|---|
| `id` | bigint | нет | |
| `building_id` | bigint → `building.id` | нет | `RESTRICT` |
| `number` | varchar(30) | нет | уникален внутри корпуса |
| `floor` | smallint | нет | ≠ 0 |
| `room_type_id` | bigint → `room_type.id` | нет | `RESTRICT` |
| `department_id` | bigint → `department.id` | да | закрепление |
| `area` | numeric(9,2) | нет | рабочая площадь, м², > 0 |
| `seats` | integer | нет | мест для обучающихся, ≥ 0 |
| `staff_seats` | integer | нет | мест для сотрудников, ≥ 0 |
| **`volume`** | integer | нет | **`GENERATED ALWAYS AS (seats + staff_seats) STORED`** |
| `is_usable` | boolean | нет | правило D6 |
| `note` | varchar(500) | да | |

Ограничения: `uq_room_building_number`, `ck_room_area_positive`,
`ck_room_seats_non_negative`, `ck_room_staff_seats_non_negative`,
`ck_room_floor_not_zero`.

**Объём помещения — вместимость в людях**, а не кубометры. Считает база
вычисляемым столбцом; приложение это значение не принимает во входных данных и
не записывает. Физический объём (площадь × высота) в системе не учитывается.

Площади хранятся как `numeric`, а не `float`: копейки квадратных метров не
должны плавать при сложении. В JSON уходят строкой с двумя знаками.

### 2.6. `room_measurement` — история обмеров

| Поле | Тип | NULL | Примечание |
|---|---|---|---|
| `id` | bigint | нет | |
| `room_id` | bigint → `room.id` | нет | `RESTRICT`, индекс |
| `area` | numeric(9,2) | нет | > 0 |
| `seats` | integer | нет | ≥ 0 |
| `staff_seats` | integer | нет | ≥ 0 |
| `measured_on` | date | нет | дата обмера |
| `measured_by_id` | integer → `app_user.id` | да | кто внёс, `RESTRICT` |
| `source` | `measurement_source` | нет | `INITIAL`, `MANUAL`, `IMPORT` |
| `note` | varchar(300) | да | |

Ограничения: `ck_measurement_area_positive`, `ck_measurement_seats`,
`ck_measurement_staff_seats`.

Запись фиксирует состояние помещения на дату обмера. История не переписывается:
исправление — это новый обмер. Помещение с историей удалить нельзя, а
`measured_by_id` защищён `RESTRICT` — автора обмера не удалить, пока его записи
существуют.

### 2.7. `discipline` и `discipline_room_type`

| `discipline` | Тип | NULL |
|---|---|---|
| `id` | bigint | нет |
| `code` | varchar(30) | нет, уникален |
| `name` | varchar(200) | нет |
| `note` | varchar(300) | да |

| `discipline_room_type` | Тип | Примечание |
|---|---|---|
| `discipline_id` | bigint → `discipline.id` | `CASCADE`, часть первичного ключа |
| `room_type_id` | bigint → `room_type.id` | `RESTRICT`, часть первичного ключа |

Матрица допустимости — связь «многие ко многим», основа правила D1. Составной
первичный ключ не даёт завести одну и ту же пару дважды.

Асимметрия удаления осознанная: удаление дисциплины уносит её строки матрицы
(`CASCADE`) — матрица без дисциплины смысла не имеет; тип помещения, на который
матрица ссылается, удалить нельзя (`RESTRICT`).

## 3. Целостность данных

Подраздел 4.1.5 ТЗ: удаление записи, на которую ссылаются другие записи,
запрещается. В схеме это все внешние ключи с `ON DELETE RESTRICT`, кроме одного
`CASCADE` в матрице допустимости.

Приложение перехватывает такие случаи раньше базы и объясняет отказ человеку:

```json
{"error": {"code": "HAS_DEPENDENTS",
           "message": "В корпусе A есть помещения (14), удаление запрещено",
           "details": {"building_id": 1, "rooms_count": 14}}}
```

Если ограничение всё-таки сработает на уровне базы, его имя переводится в
понятное сообщение по таблице `CONSTRAINT_ERRORS` в `app/errors.py`. Текст
SQL наружу не уходит.

### Где какое правило живёт

| Проверка | Уровень | Почему так |
|---|---|---|
| уникальность кодов и номеров | база + приложение | база гарантирует при гонке, приложение объясняет |
| площадь > 0, места ≥ 0, этаж ≠ 0 | база (`CHECK`) | значение проверяется само по себе |
| объём = мест обучающихся + мест сотрудников | база (вычисляемый столбец) | чтобы нельзя было записать вручную |
| прямое самородительство подразделения | база (`CHECK`) | однострочная проверка |
| цикл в иерархии длиннее одного шага | приложение | `CHECK` не умеет обходить цепочку |
| этаж существует в корпусе | приложение | нужны данные другой таблицы |
| **правило D5** | приложение | норма лежит в `room_type`, а места в `room` |
| правила D1, D2, D6 | приложение | требуют матрицы и параметров запроса |

## 4. Миграции

| Ревизия | Что делает |
|---|---|
| `0001_initial` | восемь таблиц, два перечисления, индексы, все ограничения |
| `0002_seed_reference` | начальные типы помещений с нормами площади |

Каждая миграция обратима. `downgrade` первой ревизии удаляет не только
таблицы, но и перечисления `user_role` и `measurement_source`: в PostgreSQL
они живут отдельно от таблиц, и без этого повторный накат падает с ошибкой
«type already exists».

Проверка обратимости — обязательная команда:

```bash
make migrate-check   # upgrade → downgrade → upgrade → alembic check
```

`alembic check` в конце сверяет, что модели и схема не разошлись: если кто-то
поправил модель и забыл сделать миграцию, команда об этом скажет.
